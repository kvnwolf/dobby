# 0028. Trim sweeps spend their budget on judgment, not inventory

A real `/dobby:trim-context` sweep against a 948-file repository parsed 599 files, found 306 unsupported and 43 `.sql` files that hit `parse-error`, and inventoried 24,113 comments across 1.74 MB — then stalled at 1.2% coverage and never wrote its ledger. The maintainer redid the same repository by hand as roughly 20-25 implementor lots and removed 263,238 bytes across 165 files, `bunx dobby check` green throughout and zero executable lines changed. Three rules in the shared sweep contract caused the stall, and each is replaced. First, exhaustive per-unit inventory demanded one ledger row per eligible unit — 24,113 rows — spending the whole budget on enumeration before a single judgment call; the contract now ranks one row per FILE, by the extractor's per-file comment-byte weight, and per-unit decisions happen inside the lot that touches the file. Second, requiring every batch approved before any write is unreachable at repository scale; the contract now takes one up-front approval of scope and aggressiveness, runs lots unattended, and returns to the human only when the policy changes or an outcome is blocked. Third, a `parse-error` voiding the whole sweep meant 43 unparseable `.sql` files permanently vetoed coverage genuinely earned on roughly 900 others, and every rerun restarted from zero; the ledger now records what was actually swept and reviewed, an unresolved file simply carries no `trim-context` sub-key — which already means "not covered," so no schema change — and the report names every unresolved file with its reason. The honesty invariant from ADR-0026 is untouched: the ledger never claims coverage it does not have. What changes is that missing coverage no longer erases real coverage.

The Tree-sitter extractor vendored in ADR-0027 was not the bottleneck — it ran once, cheaply, and returned a compact digest in seconds. It is retained and reframed: no longer the source of an exhaustive inventory, it is the weight and targeting input that ranks files into lots. Its `parse-error` rows still name real gaps, but they no longer block ledger finality. The recipe that actually worked carries forward four more shapes. Lots run 6-8 files by weight, sized from a failure: a 47-file lot exhausted an implementor at 13 files, 430K tokens, 257 tool calls. Each lot works one track only, comment-trim or prose densification, never both — a mixed brief produced a net −186-byte reformat instead of a real reduction. Verification is mechanical-first: a filtered `git diff -U0` proving zero executable lines changed runs per lot, and the independent `dobby:reviewer` is reserved for the judgment that diff cannot make. And levers carry forward between lots — a `CONTEXT.md` `## Files` section restating `## Interface` plus `## Invariants` gave a consistent ~−12% across lots that used it. Each brief now states its target rate explicitly (roughly 5% on code comments, 12-14% on prose), with "leave the file untouched" named as a correct outcome rather than a failure to hit a quota. Because the ledger's coverage claim now means something different than before, `rulesVersion` moves from `human-text-v1` to `human-text-v2`.

## Consequences

Coverage is now a moving target instead of a certified whole-repo baseline: a sweep can be genuinely useful while permanently short of 100%, and nothing forces the 43 `.sql` files (or their future equivalents) to ever close. Unattended lots trade approval overhead for exposure — a bad brief can burn a lot's full budget before a human sees the result, where the old contract would have stopped it at the batch gate. Mechanical-first verification proves only the executable-lines invariant; it says nothing about whether a prose or comment edit preserved meaning, so densification and slop-adjacent lots still need the expensive independent review, and that cost does not shrink just because inventory got cheaper.
