# 0032. Environment adapters become instruction catalogues

The environment seam introduced with v0.14.0 (`cli/src/environment.ts`) assumed the CLI could *execute* every host-specific mechanic — open a cmux pane, spawn a detached process, open a browser surface, rename the workspace, tear it all down. That holds only where the host is controllable from a shell. Claude Desktop and t3 code expose their surfaces as MCP tools that only the model can invoke, so on those hosts the seam had nothing to execute and no way to say so. The seam is now split into two halves with one owner each: the **mechanics half** — the setup phase, the liveness probe, pidfile registration, Neon branch provisioning, config `setup[]`/`teardown[]` extras — which `dobby` still executes; and the **instruction half** — starting the run, opening and driving the browser, renaming the workspace, stopping the run — which every adapter now *describes* per topic (`start` · `stop` · `browser` · `rename`) and the model carries out. `dobby instructions <topic>` reads the catalogue directly; `up` and `down` embed the applicable entries in a new `instructions[]` field instead of acting; `bunx dobby dev` registers its own pidfile so teardown works regardless of who launched it. Four adapters ship, one file each under `cli/src/adapters/`, detected by an ordered cascade (`CMUX_WORKSPACE_ID` → cmux; `CLAUDE_CODE_ENTRYPOINT` ∈ {`claude-desktop`, `claude-desktop-3p`, `local-agent`} → claude-desktop; `__CFBundleIdentifier` prefix `com.t3tools.t3code` → t3-code; otherwise terminal).

## Considered options

**Instructions only where the CLI cannot execute.** Keep cmux and terminal executing their mechanics as before; let only the MCP-backed hosts return instructions. Zero regression on the two adapters that worked, and the smaller change. Rejected: it leaves the seam with two contracts — a method that sometimes acts and sometimes explains — so every caller has to branch on which it got, and the executed path keeps the coupling this change exists to remove. Making every adapter an instruction catalogue gives `up`/`down` one shape everywhere and leaves nothing host-specific for the CLI to reimplement.

**A separate "unknown host" adapter.** Detect an unrecognised SDK host explicitly and answer more conservatively. Rejected: terminal's instructions (a background `Bash` job, claude-in-chrome falling back to curl) already work on any host, so the floor degrades correctly without a fifth adapter to maintain.

**Read `.claude/launch.json` on Claude Desktop** to hand the model Desktop's native `preview_start`. It is a documented, stable Desktop feature — but it names the server by a key in another product's config file while `dobby` already resolves the devUrl per worktree through portless. Two sources of truth for "how the server starts" is what we refuse; `dobby` neither reads nor writes that file, and Desktop gets the same background-`Bash` start as terminal.

**Let the model write the pidfile.** The start instruction could include writing `.dobby/dev.pid` after the spawn. Rejected: the process that starts *is* `dobby dev`, so it registers itself — ownership no longer depends on who launched it, `killFromPidfile`'s ownership check (a `ps` command match within 15 s of the file's mtime) keeps working, and `dev` can refuse a live twin instead of orphaning it. Because a model-launched process is not guaranteed to lead a process group, `killFromPidfile` now signals `pid` rather than `-pid`; `dev`'s own SIGTERM handler tears its children down.

## Consequences

`up` no longer knows synchronously whether a start succeeded — the old `dev-start-failed` reason is gone. The trade is favourable: the model that ran the start command sees its full stderr, which is more than the old boolean ever said, and a second `up` distinguishes "start in flight" (a live registered pidfile → the existing liveness loop) from "nothing started" (→ the same instruction again, which the bring-up protocol treats as a stop-and-report). The two-step bring-up now lives once, in `plugin/skills/execute/references/bring-up.md`, cited by every skill that used to promise "`up` ensures the run is up".

Idempotency of the browser surface moved from code to text: under cmux the instruction embeds the pane ref `list-panes` discovery found, so the model never decides whether to open a second pane; behind an MCP browser only the model can query the state, so those guides lead with their own status call (`preview_status`, `tabs_context`).

Two adapters carry explicit limits. t3 code injects no variable of its own, so its detection rests on a macOS bundle id — on Linux and Windows it falls to terminal and loses its browser guide. The Claude Desktop adapter is written from a field study (`docs/field-studies/claude-desktop-2026-08-19.md`; public docs confirm the entrypoint values and the server name `Claude Browser`, not its eighteen method names) and is marked `unverified` in code until someone runs it against a live Desktop.

ADR-0031's vendored cmux protocol is unchanged in content but changed in channel: it is now the cmux adapter's `browser` instruction, served by `dobby instructions browser`, and `dobby env` reports facts only.

## Accepted residual risk: the registry is a pidfile, not a lock manager

The registry went through five review rounds of concurrency hardening (atomic `O_EXCL` create, reclaim by `rename` with re-classification, a three-way ownership verdict where an inconclusive `ps` never deletes and never reclaims, and a teardown sweep of `dev.pid.stale.*` sidecars). What remains is deliberately left open: `up` and `dev` arbitrate on `dev.pid` alone, so a live registration that a failed restore stranded in a sidecar — which takes three `dev` processes overlapping inside one rename window — is not seen by `up` until `down` sweeps it. Reading sidecars at startup was considered and rejected: it would let an orphaned sidecar under a broken `ps` (verdict `unknown`, therefore "alive") block every `up` until a manual `down`, extending a degraded mode into ordinary operation. The kit's own flow never produces the precondition (the model runs one `start` per instruction and verifies it before re-invoking `up`), `dobby dev` refuses while `dev.pid` is live, and portless refuses a second `run` on the same route. A registry that tried to close this too would be a lock manager, and that is not the module's job.
