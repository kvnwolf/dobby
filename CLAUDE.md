# dobby — working on this repo

This repo is a Bun monorepo shipping two surfaces: **`plugin/`** — the Claude Code plugin (skills, agents, hooks) — and **`cli/`** — the `@kvnwolf/dobby` CLI. The repo is ALSO its own marketplace: `.claude-plugin/marketplace.json` stays at root and points at `./plugin`. `README.md` is the consumer-facing doc; this file is for evolving the kit itself.

The domain glossary lives in [`CONTEXT.md`](./CONTEXT.md) — use those terms exactly.

**The kit runs on a single execution host: the terminal** — a plain interactive `claude` session (incl. ssh, and inside cmux) where Claude Code owns tools, sessions, hooks, worktrees, background agents, and the native Workflow runtime. `/dobby:scope` creates+enters the per-goal worktree (native `EnterWorktree`) and brings it up via `bunx dobby up` (which runs the setup phase — install + env-file materialization — then starts the app; idempotent, so `/dobby:execute` Step 2 re-runs it without double-starting), and `/dobby:finish` closes the goal — it merges the goal's PR behind an explicit gate (squash, only on the user's "Merge & finish" selection and only once `dobby pr watch` reports merge-ready) when the PR is still open, then tears the worktree down via `bunx dobby down`. **cmux enrichment** (named run/browser panes, cmux-browser UI driver) kicks in when `CMUX_WORKSPACE_ID` is set, degrading gracefully to a detached background job otherwise. The mechanical layer is the `@kvnwolf/dobby` CLI — each consumer's single devDependency — which the skills invoke via `bunx dobby`: `env` (environment snapshot + authoritative fixed Workflow recipe), `check` (the quality gate + edit-time hook; `check --fix` is the pre-commit gate), `up`/`down`/`dev` (the run lifecycle — `up` folds in worktree setup), and the inferred `db:*` / `update` tasks. The coordinator + verifier reach the running app via the devUrl `bunx dobby up` reports; `execute` separately resolves `workflowRecipe` with `bunx dobby env --json`. Dobby never launches `claude -p` or another agent CLI to execute workers. (Conductor, the former second host, was removed; [ADR-0010](./docs/adr/0010-single-terminal-host.md) documents what it did, for a possible future re-add.)

## Structure

- `.claude-plugin/marketplace.json` — the marketplace manifest, kept at root; its `plugins[0].source` is `./plugin`, making the repo installable directly.
- `plugin/` — the Claude Code plugin itself (self-contained; cache-copied on install, so it can never reference `../cli`). Module doc: [`plugin/CONTEXT.md`](./plugin/CONTEXT.md).
  - `plugin/.claude-plugin/plugin.json` — the plugin manifest.
  - `plugin/skills/` — the kit's skills, one directory per skill (`SKILL.md` + optional `references/` / `examples/` / `scripts/`). A skill's `scripts/` may carry vendored runtime assets when self-containment demands it — `trim-context/scripts/vendor/` holds the Tree-sitter WASM runtime and grammars its comment census parses with, each recorded in `PROVENANCE.md` with package, version, licence and SHA-256 ([ADR-0027](./docs/adr/0027-vendor-tree-sitter-wasm-inside-the-trim-context-skill.md)).
  - `plugin/agents/` — the five authoritative worker-agent definitions (`researcher`, `test-author`, `implementor`, `reviewer`, `verifier`). `test-author` writes tests from the spec only (never seeing the implementation) and runs at the front of the build loop; see [`CONTEXT.md`](./CONTEXT.md) for the build-loop shape.
  - `plugin/hooks/` — `hooks.json` (auto-loaded when the plugin is enabled): the PostToolUse `Edit|Write` hook invokes the consumer's LOCAL `node_modules/.bin/dobby check --hook` behind a `dobby.config.json` guard (never `bunx`, which would fetch the foreign npm `dobby`), so edit-time formatting is auto-fixed in place and only unfixable findings reach the model.
- `cli/` — the `@kvnwolf/dobby` Bun CLI workspace (the monorepo's `workspaces` member): the kit's **mechanical execution layer** — capability detection + zero-config task inference, the quality gate (`check`), the run lifecycle (`up`/`down`/`dev` — `up` folds in worktree setup), and the `env` snapshot plus fixed native Workflow recipe the skills read. `cli/src/workflow-recipe.ts` is the single source for agent model/effort and build-loop limits. Installed as each consumer's single devDependency; bundles the toolchain (Biome, TypeScript, knip, taze, portless) and exposes shared `tsconfig`/`biome` presets — the `tsconfig` extended in one line, the `biome` presets shipped FLAT (`biome/core` + `biome/react`) so a consumer with lint/format deltas extends both directly (biome's `extends` is one-level/non-transitive) while a delta-less consumer ships no `biome.jsonc` at all. It also ships `cli/grit/` — the house conventions biome's native rules can't express, as GritQL linter plugins wired into the config-less react preset path (module doc: [`cli/grit/CONTEXT.md`](./cli/grit/CONTEXT.md), which carries the per-rule shipped/partial/parked verdicts). Module doc: [`cli/CONTEXT.md`](./cli/CONTEXT.md); the npm-facing reference is [`cli/README.md`](./cli/README.md).
- `docs/` — the kit's **durable artifacts** written by skills as work proceeds: `adr/` (architecture decision records from `/dobby:wrap` + `/dobby:address-review`), `maps/` (decision-maps from `/dobby:map`), `out-of-scope/` (the out-of-scope KB from `/dobby:triage`, one file per concept), `learn-discarded/` (the discarded-frictions KB from `/dobby:learn`). Committed and git-tracked; the KB dirs are created lazily by their skills (no empty dirs committed). STATE.md stays ephemeral at the repo root — it is NOT a durable artifact.
- `README.md` — the FULL consumer doc: install, mental model, lifecycle, first-session walkthrough, decision table, troubleshooting. Behavior changes to skills/agents must keep it in sync.

There is intentionally no `.claude/` self-install in this repo: the plugin is enabled at user scope (global `settings.json` registers this working tree as the `dobby` marketplace with `autoUpdate`), so every project — including this one — consumes it live. A project-level install here would re-register the same marketplace name from a different source.

## Conventions

- **Dogfood the kit**: evolve dobby through its own stages (`/dobby:scope` → … → `/dobby:wrap`) or `/dobby:dispatch` for small fixes. Friction found while doing so is signal — fix the kit, not the workaround.
- **Everything in English.** Three skill categories coexist. (1) The work-session **stage** skills (`scope` → … → `wrap`), the **side-path** skills that plug into the flow on demand (`handoff`, `triage`, `map`, `resolve-conflicts`, `wizard`, `teach`, `upgrade`), the worker agents, and their supporting skills are **methodology** — project-agnostic (no references to any specific codebase) but assuming the single **terminal execution host** (with optional cmux enrichment when `CMUX_WORKSPACE_ID` is set) and delegating environment mechanics to the `@kvnwolf/dobby` CLI (`bunx dobby` — `env`/`check`/`up`/`down`/`dev`/`db:*`/`update`); the kit reaches the running app via the devUrl `dobby env` reports plus a curl liveness check, and drives the UI via the cmux-browser → claude-in-chrome → curl ladder; see the statement above). (2) The kit ALSO carries **convention** skills (`data-processing`, `data-fetching`, `module-conventions`) that encode the user's standard application stack (TanStack Start + Drizzle/Neon + Better Auth, the `@/shared` form/data system) and intentionally reference its module file conventions — deep-path imports and the role-based file taxonomy (`{export}.server.ts` / `functions.ts` / `{descriptor}.browser.ts` / `schema.gen.ts`), no barrels. That coupling is deliberate, not a leak to genericize. (3) **Kit self-improvement tooling** (`mark`, `learn`) couples to the *host* — Claude Code session storage (`~/.claude/projects`, `CLAUDE_CODE_SESSION_ID`) — not to any project, and exists to evolve the kit from how it behaved in real field sessions. That host-coupling is intentional and each such `SKILL.md` must label itself as this category so it isn't mistaken for project-agnostic methodology.
- **Skills carry NO `model:`/`effort:`; the fixed recipe has one owner.** Skills inherit the interactive SESSION's model/effort; the maintainer chooses the main-thread Architect's intelligence manually for the task. Agent PROMPT BODIES in `plugin/agents/*.md` remain the authoritative role instructions and are edited there exactly once. `cli/src/workflow-recipe.ts` owns `baseline-v1`: researcher Sonnet/medium, test-author Opus/high, implementor Sonnet/high, reviewer Opus/high, verifier Sonnet/medium, plus `maxOuter=2`, `maxConcurrency=2`, and mechanical-first verification. Agent frontmatter mirrors direct-call values; the native build Workflow applies the relevant role values per invocation, and drift tests keep both surfaces aligned. There is no normal execute reviewer loop or `maxReview`; reviewer remains available for explicit dispatch and missing-work-log safety review. There are no Dobby budget profiles, selection prompt, config files, environment overrides, or CLI flags during this seven-day baseline experiment. Claude Code's operator-level `CLAUDE_CODE_SUBAGENT_MODEL` may still override subagent pins externally; record that when evaluating a run because it is host control, not a Dobby recipe input.
- **Namespacing is mandatory**: cross-references between kit pieces are always `/dobby:<skill>` and `dobby:<agent>`. Bare names only for things outside the plugin. After any rename/addition, grep for bare references.
- **The Architect never implements.** The interactive main thread owns planning, host mechanics, `AskUserQuestion`, persistence, routing, and worker dispatch. It delegates exploration and code changes to workers; a stage skill that makes main grep around or implement code is a regression.
- **The fixed concurrency cap covers every fan-out.** Before any skill launches more than one direct Agent, it resolves `workflowRecipe.limits.maxConcurrency` with `bunx dobby env --json`, fails closed on malformed/missing data, and runs deterministic sequential batches no larger than that limit. This includes research, interview-requested research, dispatch, address-review, improve-architecture, and resolve-conflicts; the build Workflow enforces the same cap internally.
- **Spec prefers scoped evidence but keeps the original standalone path.** In a work session, `/dobby:spec` writes only the existing `STATE.md`; for an already-understood standalone task with no state, it may run `dobby state init` before persisting and linting the plan. It never invents missing understanding—when inputs are thin, route to interview/research instead.
- **No interruptions mid-flow**: stages run to completion; gates exist only at stage handoffs (Next-step) and plan approval. No unsolicited explanations; teaching is opt-in via `/dobby:teach`.
- **Stage handoffs gate on an AskUserQuestion**: a stage ends with an AskUserQuestion at the Next-step — the recommended next `/dobby:*` command plus alternatives and "Stop here" as options; on selection the chosen skill is invoked. Since skills no longer carry their own `model`/`effort`, there is no per-skill tier to preserve by typing — the session's model/effort applies throughout, so invoking the next skill on selection is correct. (This Next-step AskUserQuestion IS the "gates exist only at stage handoffs and plan approval" gate above.)
- **Preserve attributions** (e.g. `prototype` is adapted from mattpocock/skills).

## Dev loop

- Test locally: `claude --plugin-dir ./plugin` from any project, then exercise the skills there.
- `SKILL.md` edits hot-reload; changes to `plugin/agents/` or `plugin/hooks/` need `/reload-plugins`.
- Manifest sanity: root `.claude-plugin/marketplace.json` and `plugin/.claude-plugin/plugin.json` must both stay parseable; the marketplace `source` stays `./plugin`.
- Aggregate gate: **`bunx dobby check`** from the repo root — Biome (lint + format) + `tsc --noEmit` + knip + vitest, plus the kit-specific `dobby.config.json` `checks[]` (manifest-parse + agent frontmatter) — is the whole-repo quality gate, mirrored by CI and by `/dobby:commit` (which reaches it through `bunx dobby ship`'s in-process `check --fix`). The repo dogfoods its own CLI: dobby is the single devDependency (`workspace:*`), the root `tsconfig.json` / `biome.jsonc` are thin files extending `@kvnwolf/dobby/*`, and there is no `vite.config.ts`. As the single-package-exception consumer (monorepo inference is out of scope in v1), the `cli/` workspace is covered by pointing those root configs at `cli/src`.

## Workflow config

- **Dev command**: `claude --plugin-dir ./plugin` (no dev server or URL — this is a Claude Code plugin, not an app). `/dobby:execute`'s verifier exercises skills through that host session.
- **Recipe contract**: `bunx dobby env --json` always reports the immutable `workflowRecipe.id: baseline-v1` plus its deterministic fingerprint. `/dobby:execute` passes the complete object into ONE native Workflow run, which recomputes the fingerprint before any Agent, applies model/effort through native `agent()` options, and enforces 2 outer attempts, concurrency 2, mechanical-first verification, telemetry, and the no-terminal-fix invariant: a fix is legal only while another verifier attempt remains. Normal execute is optional test-author → implementor → verifier; static holistic review happens at the external PR boundary, and current-HEAD freshness is mandatory before merge readiness. A write-capable Agent with no usable work log consumes an independent safety review and remains `needs-human`. The runtime exposes no same-role build-thread resume or direct shell primitive, so Dobby neither promises reuse nor emulates it with subprocesses. See [ADR-0023](./docs/adr/0023-fixed-baseline-workflow-recipe.md) and [ADR-0024](./docs/adr/0024-external-pr-review-boundary.md).
- **Commit contract**: **`bunx dobby ship`** is the ceremony — stage → the in-process `dobby check --fix` gate → re-stage → commit → push → `gh pr create` off a non-trunk branch — and a red gate commits nothing (its findings printed whole, its exit code returned). `/dobby:commit` keeps the judgment (doc-sync, message + PR-body authoring, the `dobby goal parse` lifecycle link) and delegates every mechanic to `ship`, then watches the PR with `bunx dobby pr watch --await-review --json`. The gate itself lives in `dobby check`, and a **pre-push backstop** — a git `pre-push` hook installed idempotently by `dobby up`'s setup phase — re-runs it (`dobby check --pre-push`, full findings, gate-cache short-circuit) so a red gate can never reach the remote; `git push --no-verify` bypasses it. `dobby.config.json` holds `files[]` (doc-sync rules — README/CLAUDE/CONTEXT/cli CONTEXT) plus optional `checks[]` extras (this repo declares its checks explicitly — the monorepo-inference exception, e.g. manifest parse + frontmatter model/effort on agents) that run AFTER the inferred gate.
- **Releases**: `/dobby:release` cuts the npm release of `cli/` (the `release` key in `dobby.config.json` declares the target) — main checkout only, per [ADR-0008](./docs/adr/0008-zero-framework-portable-cli.md). A release that asks anything of a consumer (new hook, new config key, absorbed skill, rules that can go red) also ships an upgrade note at `plugin/skills/upgrade/references/v<minor>.md` — `/dobby:upgrade` walks those notes when consumers jump versions.
