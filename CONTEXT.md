# Domain glossary

The vocabulary of the dobby kit. Use these terms exactly — in skills, agents, docs, and conversation.

- **Execution host** — WHERE a work session runs. There is a SINGLE host: the **terminal host** (see its own entry). The KIT owns the run lifecycle — the session itself runs inside whatever checkout or worktree the operator opened; the coordinator and **QA** reach the running app via the devUrl `dobby env` resolves (portless-based, distinct per worktree) plus a curl liveness check — not by reading a run-script terminal — and drive the UI per **instruction catalogue** (`dobby instructions browser`, which is cmux's own ladder — cmux-browser → claude-in-chrome → curl — under cmux, and a different guide under Claude Desktop / t3 code). (Conductor, the former second host, was removed; everything it did is captured for a possible future re-add in [ADR-0010](./docs/adr/0010-single-terminal-host.md).)
- **Terminal host** — the kit's single execution host: a plain `claude` session (incl. ssh, and inside cmux), operated inside whatever checkout or worktree the operator already opened — the KIT owns the run lifecycle, not the worktree itself. `/dobby:scope` grounds the goal where the session stands, writes `STATE.md` there, and brings it up via `bunx dobby up` (setup phase + probe), which `/dobby:execute` Step 2 re-runs idempotently; `/dobby:finish` closes the goal — merging its PR behind an explicit gate when it is still open, tearing the run down via `bunx dobby down`, and, only when the session stands in a linked worktree, offering to remove it. Environment mechanics are no longer fully delegated to the CLI — `dobby` detects the environment and hands the model an **instruction catalogue** entry for what it cannot do itself (starting the run, opening a browser, renaming the workspace, stopping the run), while `up`/`down` still execute the setup phase, the liveness probe, pidfile registration, Neon branch provisioning, and config `setup[]`/`teardown[]` extras. See also **cmux enrichment**, **Instruction catalogue**.
- **cmux enrichment** — the optional layer that activates when `CMUX_WORKSPACE_ID` is present (auto-set in every cmux pane; cmux = the manaflow-ai native macOS terminal). `bunx dobby up` no longer opens the kit panes itself — its `start`/`rename` **instructions** tell the MODEL to open them (a named run pane `dobby-run-<slug>`, a named browser pane `dobby-browser-<slug>`, and renaming the cmux workspace itself to the goal slug), embedding the refs its `list-panes`/`list-pane-surfaces` discovery found so the model reuses an open pane instead of always opening one; `bunx dobby down`'s `stop` instruction likewise tells the model which panes to close. `bunx dobby env` still surfaces the pane refs (`runPane`/`browserPane`, rediscovered by title) for a caller that only needs to read them. A plain terminal (ssh/tmux, no `CMUX_WORKSPACE_ID`) degrades gracefully: its `start` instruction is a background `Bash` job instead of a cmux pane, and `stop`/`rename` never apply.
- **Instruction catalogue** — what an **environment adapter** delivers: per-**topic** instructions the MODEL executes because `dobby` cannot act there on its own behalf. This is the "instruction half" of the environment-adapter seam; the "mechanics half" — the setup phase, the liveness probe, pidfile registration, Neon branch provisioning, config `setup[]`/`teardown[]` extras — is what `dobby` still executes itself. `dobby instructions <topic> [--json]` reads one entry directly; `up`/`down` embed the applicable ones in their own `instructions[]`.
- **Topic** — a unit of the **instruction catalogue**: `start` (bring the run up), `stop` (tear it down), `browser` (drive the UI), or `rename` (retitle the workspace to the goal slug). A topic that does not apply in the detected environment (e.g. `rename` on a plain terminal, which has no workspace to rename) is a valid answer — `applies: false` — never an error.
- **Environment adapter** — detection plus the **instruction catalogue** for ONE host: `cmux`, `terminal` (the floor), `t3-code`, and `claude-desktop` — one file each under `cli/src/adapters/`, resolved once per command by `detectEnvironment()`. Formerly an implementation that EXECUTED mechanics (opening panes, spawning the run) on the kit's behalf; now it only discovers surfaces (so an instruction's text can embed a ref) and answers the catalogue — the model carries out everything the instruction names.
- **Run script** — the command that starts the app. It is NO LONGER a config key: `dobby dev` INFERS it from the project's detected capabilities (zero-config à la Vercel; see **Task inference**) — the main dev server wrapped in **portless**, plus any capability-detected secondaries (e.g. react-email) run concurrently. `dobby up` no longer starts it itself — it hands the model the `start` **instruction**, and `dobby dev` registers its own pidfile on startup so a later `up`/`down` can find and manage it. The `portless get` identity is UNCHANGED: the dev URL is obtained deterministically via `portless get <name>` — worktree-branch-prefixed (portless's own behavior, so distinct per worktree), resolved never parsed from terminal output — and `dobby env` reports it as `devUrl`; liveness is a curl health-check against that URL. A project with no app (a lib/CLI/plugin like dobby itself) infers no dev command, so `devUrl` is null, `up`/`down` no-op the run cleanly, and **QA** verifies programmatically.
- **up / down** — the run-lifecycle pair the `dobby` CLI exposes, mechanizing `/dobby:scope`'s bring-up, `/dobby:execute` Step 2, and `/dobby:finish` teardown. **`dobby up`** prepares the workspace AND probes it — it no longer starts anything itself: a **setup phase** (`bun install` + `.worktreeinclude` re-materialization + any `setup[]` config extras — worktree prep is folded into `up`, not a separate command), then a single liveness probe; already live, or a start already in flight (found via its **pidfile**) → wait it out; otherwise it hands back the applicable **instructions** (`rename` under cmux, then `start`) for the model to carry out and re-invoke `up` with — the two-step protocol every skill/agent that brings a worktree up follows. A no-app project finishes the setup phase, still gets its `rename` instruction under cmux, and reports 'no app to run'. For a neon-capability project it provisions a per-worktree branch and rewrites `.env.local` (missing creds → hard fail, never a silent fallback to the shared DB). **`dobby down`** tears its OWN mechanics back down, best-effort — kills the registered pidfile process, deletes the neon branch, runs `teardown[]` extras — and hands back the `stop` instruction (closing any discovered kit pane) for the model to carry out.
- **Architect** — the interactive main Claude Code thread. It frames the task, interviews the user, synthesizes worker research, authors the spec, invokes public skills, operates worktrees and the CLI, dispatches workers, persists state, approves routing, and owns every decision. It NEVER implements code or spends its context grepping the codebase; those hands-on jobs belong to **Workers**. Skills inherit this session's model/effort, which the user chooses manually for the task.
- **Coordinator** — the mechanical facet of the **Architect** while workers run: host-only operations such as public skill invocation, worktree and CLI commands, worker dispatch, `AskUserQuestion`, persistence, approval, routing, cancellation, and handoff. It is not a separate agent or planning thread.
- **Worker** — one of the five custom hands-on agents: `researcher`, `implementor`, `reviewer`, `qa`, and `test-author`. Each has a fixed role and toolset, with its prompt body authoritative in `plugin/agents/`, and model/effort declared directly in that same frontmatter — there is no external recipe to mirror.
- **Work session** — one end-to-end run over a single goal, moving through stages: scope → interview → research → spec → execute → wrap.
- **Stage** — one step of a work session. Each stage is a skill that does its job and ends at a Next-step AskUserQuestion gate (the recommended next `/dobby:*` command, alternatives, Stop here); the chosen skill is invoked on selection. Skills carry no per-skill model/effort — the session's tier applies throughout (ADR-0004).
- **Finish** — the goal-closing stage (`/dobby:finish`): a manual command run once the PR is merged — or merge-ready, since its confirm gate offers **Merge & finish** on an OPEN PR with a clean tree (a squash `gh pr merge`, fired ONLY on that explicit user selection and only after `dobby pr watch` answers `merge-ready`, then a preflight re-read). It checks the PR is MERGED (confirming before merging or destroying anything otherwise), runs **`bunx dobby down`** (which kills the registered run process, deletes the per-worktree Neon branch, and runs the config's `teardown[]` extras — then hands back the `stop` instruction for the model to close any kit-opened cmux pane with), and then: when the session stands in a linked worktree (whoever made it), offers to remove that worktree + branch (native `ExitWorktree` first, then raw git from the main root for an orphan); on a plain checkout, returns to `main` and deletes the goal's branch instead. `git pull` always runs on the main checkout.
- **One session per goal** — each session/pane owns ONE goal at a time, worked wherever that session stands. It is NOT "one worktree per machine" — MULTIPLE goals run in PARALLEL worktrees, one per cmux pane/session (the cmux value-prop), each opened by the operator (or the host) rather than by the kit. Teardown is per goal via `/dobby:finish`.
- **Goal slug** — the kebab-case identity a work session is known BY: `basename(workroot)` — the name of whatever checkout or worktree the session already stands in, never a kit-assigned one. The cmux workspace title, the kit pane titles and the per-worktree neon branch all derive from it. A free-text goal slugs its own text; an ISSUE goal LEADS with the tracker's id — `issue-42-add-csv-export`, `von-123-fix-stale-session-cache` — so the issue stays recognizable wherever the name gets clipped.
- **Context trim** — the inference-only `/dobby:trim-context` sweep that lowers the token/context cost of human-authored repository guidance and comments without changing behavior. It ranks the whole Git workroot by weight, obtains one up-front approval of scope and aggressiveness, runs unattended lots against that approval, and independently reviews every approved write. It is the sole owner of comment changes. It is not a **Gate** and never adds CLI, configuration, tooling, or executable behavior.
- **AI slop** — generic AI-writing patterns that weaken a specific prose or user-facing-copy unit's clarity, specificity, voice, or purpose. `/dobby:anti-slop` identifies and makes minimum contextual fixes to AI slop without inferring authorship, assigning scores, banning occurrences, or editing comments. When both inference sweeps apply, **Context trim** runs before AI slop.
- **Sweep ledger** — the tracked state file `.dobby/sweeps.json` that records reviewed sweep coverage with a rules version and SHA-256 hashes of exact final file bytes, keyed per file **and per skill**: each file's entry may hold a `trim-context` sub-key, an `anti-slop` sub-key, or both, and coverage accrues incrementally — an unresolved file simply carries no sub-key for that skill rather than voiding the sweep. Each skill reads and writes only its own so the two sweeps coexist without one invalidating the other's coverage. It is the deliberate exception to the inference-only/no-Gate boundary: persistent coverage state, not a configurable or executable surface.
- **Load tier** — an eligible human-text unit's context exposure tier, not an editorial-quality rating: tier 1 directs agent behavior (root instructions, skills, agents, glossary); tier 2 is repeatedly consulted while working (`CONTEXT.md`, module and operational guidance); tier 3 is read only for a narrow file or task (general docs and comments). Inference sweeps present approval batches in tier order.
- **Convention skill** — a skill that encodes the user's standard application stack (TanStack Start + Drizzle/Neon + Better Auth, the `@/shared` form/data system) rather than methodology: `data-processing`, `data-fetching`, and `module-conventions`. It auto-activates while building, intentionally references the consuming project's module file conventions (deep-path imports and the role-based file taxonomy — no barrels), and is NOT a work-session stage.
- **STATE.md** — the ephemeral session doc at the target repo's root, normally created by `/dobby:scope`; a standalone `/dobby:spec` may initialize the same skeleton for an already-understood task. SEVEN canonical sections, in this fixed order: `## Goal`, `## Source`, `## Exploration`, `## Findings (interview)`, `## Research`, `## Spec`, `## Work log`. Its engine is the CLI's **`dobby state`** command — `init` (the skeleton + the `.gitignore` entry), `set <Section>` (replace ONE body, every other byte preserved; `## Goal`/`## Source` are write-once), `append-worklog --task <id>`, `lint` (the structural report) — so no stage hand-rewrites the document. Unknown legacy sections, including retired `## Execution profile`, are tolerated and preserved but never created or deleted automatically. Disposed at wrap — it is never committed.
- **`docs/` durable artifacts** — where the kit's skills write knowledge that OUTLIVES a work session (the durable counterpart to the ephemeral `STATE.md`). All under the project's `docs/` tree, committed, created lazily (never an empty dir): the **decision-map** at `docs/maps/` (`/dobby:map`'s dependency-linked investigation tickets for one planning effort), the **out-of-scope KB** at `docs/out-of-scope/` (`/dobby:triage`'s rejected enhancement requests, one concept file each), and the **discarded-frictions KB** at `docs/learn-discarded/` (`/dobby:learn`'s field frictions deliberately NOT turned into skill edits, one concept file each). ADRs stay in `docs/adr/` (project-owned, standard convention); `STATE.md` stays ephemeral at the repo root.
- **dobby.config.json** — the kit-owned per-project contract at the repo ROOT (next.config.js style — not `.claude/`, which is the host's reserved namespace). JSON, shrunk to `files[]` (doc-sync `update_when` triggers) plus OPTIONAL `setup[]` / `teardown[]` / `checks[]` extras that run AFTER (in addition to) the capability-inferred defaults, and two optional session keys — `tracker` (the per-project issue backend — see **tracker**) and `release` (the publish target, whose PRESENCE is what makes `dobby release` exist — see **release adapter**) — the old `run` key, task lists, and worker model/effort policy do not belong here. The `dobby` CLI is its sole reader of the mechanical keys: `check` folds in `checks[]`, `up` runs `setup[]` (in its setup phase), and `down` runs `teardown[]`. `files[]` stays skill-consumed (`/dobby:commit`, `/dobby:resolve-conflicts`); the `tracker` and `release` keys are read by the CLI too. Its presence at the root is ALSO the "dobby project" marker the edit hook guards on. Written by `/dobby:onboard`; existing repos upgrade via `/dobby:upgrade`, which routes a legacy `.claude/commit.config.yml` + vite-plus repo through `/dobby:migrate-config`'s clean cut.
- **tracker** — the per-project issue backend the work skills read and write, selected by the optional `tracker` key in **dobby.config.json**: **GitHub Issues** by default (the `gh`-authenticated repo; key absent or `type: "github"`), **Linear** (`type: "linear"` + a `team` key like `VON`), or **local** (`type: "local"`, a plain `BACKLOG.md`). GitHub keeps a natural `repo → tracker` derivation (zero-config); Linear needs the `team` key because it has none. _Avoid_: issue tracker, ticket system.
- **release adapter** — the per-TARGET publisher behind `dobby release`'s shared spine (preflight → version → bump → changelog → publish), selected by the `release.type` key in **dobby.config.json**: **npm** (`dir`, `lockstep`, `surfaces`, `smoke`) or **homebrew-cask** (`tap`, `cask`, plus the two extra phases it adds). The spine knows the PHASES and owns every ordering scar (publish-gated push, rollback before the tag); the adapter knows only what is channel-specific (`npm publish`, the tap checkout + cask checksum). Nothing in a repo infers a target, so NO `release` key means the command does not exist at all. `/dobby:release` is its skill. _Avoid_: publisher plugin, release backend.
- **Design tree** — the dependency structure of a task's open decisions in `/dobby:interview`: every question hangs off the answers or research it depends on, and each answer pushes the **frontier** outward.
- **Frontier** — every open decision in the **design tree** whose prerequisites are already settled: everything `/dobby:interview` could ask RIGHT NOW without guessing — what a **round** asks, split across consecutive rounds by the four-question popup cap and by vehicle; the interview closes only when it is empty.
- **Round** — one turn of frontier questioning in `/dobby:interview`, homogeneous by vehicle: an `AskUserQuestion` batch of AT MOST four questions with anticipatable options, or a plain-text batch of open-ended ones.
- **Build loop** — the per-task loop that turns a spec into locally verified code: `test-author` (conditional — only when the repo has a test suite AND the spec marked the task test-first) → `implementor` (implements, then runs its own **Exit gate**) → **QA** (proves real behaviour and returns a verdict). A defect QA finds opens a **build conversation** with the implementor, or with the test-author when the failure traces to the test contract rather than the implementation; that conversation is capped at five rounds, after which QA reports the task `needs-human` instead of retrying further. Normal execute never dispatches the reviewer — holistic static review lives at the **External PR review boundary**. Encoded once in the `dobby:execute` skill's `references/build-protocol.md` — the dispatch protocol the Architect follows directly, for every task — and reused by `/dobby:dispatch` and `/dobby:address-review`, which follow that same protocol for a single ad-hoc task instead of a whole plan.
- **QA** — the worker (`dobby:qa`) that runs the build loop's last step: proves a task's real BEHAVIOUR ONLY, never lint, types, build, or the test suite — that mechanical layer is already closed by the **Edit hook** and the implementor's own **Exit gate** before QA is ever dispatched. It drives the browser (following `dobby instructions browser`, the environment's own **instruction catalogue** entry for the UI-verification topic — never `env`, which reports no browser guide) where an app exists, or exercises the artefact directly (a CLI, a skill, a library) where none does, and returns `{pass, failureKind, evidence, verificationKind, findings}`. A genuine defect opens a **build conversation** with the implementor or test-author; QA never edits code itself. _Avoid_: verifier.
- **Build conversation** — the direct sibling `SendMessage` exchange that closes a build-loop failure: QA reaches back to whichever worker can fix it — `dobby:implementor` for a code defect, `dobby:test-author` (describing expected behaviour only, never a code fragment) for a test-contract problem — rather than starting a fresh agent that would re-read everything. QA numbers every message in the text itself (round 1, round 2, …), so the count survives a fresh context on either side; the conversation is capped at five rounds, after which QA stops and reports the task `needs-human`. An environment failure (a dead browser, an expired credential, anything QA can't attribute to the code or the tests) never enters this conversation — it goes straight to the Architect and costs no round.
- **Test-author** — the worker (`dobby:test-author`) that runs the conditional first step of the build loop: it writes a task's tests **from the spec alone, never seeing the implementation**, producing the fixed contract the implementor must satisfy. Blindness to the code is what makes the tests anti-tautological — an independent source of truth. It runs once per task; a **build conversation** round re-implements against the same tests without the test-author touching the implementation itself, the implementor's own **Exit gate** runs them, and the external PR reviewer later judges their static quality in the context of the complete change.
- **Green baseline** — the record (`dobby baseline record`, stored at `.dobby/baseline.json`) of which test suites were already failing before a task's work began. The implementor's **Exit gate** consults it (`dobby check --fix --baseline`) so only suites newly red because of this change are reported — a pre-existing failure is exempt, not the implementor's to fix. It replaces hand-written KNOWN-RED exclusions, and an absent record is stated explicitly ("every failing suite counts") rather than passing silently. Distinct from the **gate cache**, which records only proven-GREEN verdicts, never pre-existing red ones.
- **Exit gate** — the full `dobby check --fix --baseline` the implementor runs on itself before handing a task to QA, serialised to one implementor at a time across the shared tree (a task's other steps — its test-author step, its implementation, its QA proof — keep running in parallel with its siblings; only the gate itself queues, because it judges the whole tree). This INVERTS the earlier rule that forbade implementors from running any check: the mechanical layer is closed before QA ever sees the task, which is what lets QA prove behaviour only and never re-run it.
- **Work log** — the per-task implementation record (diff summary, decisions, deviations) an implementor RETURNS (it never writes `STATE.md`); the coordinator appends entries serially as the single writer.
- **Verify recipe** — the per-task steps a QA agent executes against the already-running app to prove the task works. Written at spec time, consumed at execute time.
- **External PR review boundary** — the holistic static-quality gate after commit/push. The normal build loop proves each task locally and does not duplicate the repository's reviewer; `dobby pr watch` requires the configured external review (currently Greptile) to cover the current PR HEAD before it can report `merge-ready`. A stale summary or review silence is `open-unreviewed`, never success. The explicit `dobby:reviewer` agent remains for direct review dispatch and missing-work-log safety review. See [ADR-0024](./docs/adr/0024-external-pr-review-boundary.md).
- **needs-human** — terminal task status when a task's **build conversation** exhausts its five rounds without QA passing it, or when a possibly mutating writer returned no usable work log. The build loop doesn't thrash or dynamically change models; it stops and returns control to the human.
- **blocked** — a terminal task state alongside done/needs-human: the task was skipped WITHOUT spawning agents because a direct or transitive dependency ended `needs-human`; the result names the blocker (`blockedBy`) and the task gets no work-log entry. Transitivity is structural — a blocked task is itself non-`done`, so its own dependents block in turn — while every task independent of the dead one keeps running exactly as if nothing had happened. _Avoid_: skipped, cancelled.
- **Dispatch** — the lightweight ad-hoc path: a scoped task handed to one worker (or the single-task build loop), no `STATE.md`.
- **Prototype** — throwaway code that answers ONE design question, then dies. Two branches: **logic** (a minimal TUI over a pure, portable module) and **UI** (3-5 radically different variants on one route with a floating switcher).
- **Namespacing** — inside the plugin, every cross-reference is fully qualified: `/dobby:<skill>` for skills, `dobby:<agent>` for `subagent_type`/`agentType`. Bare names are reserved for things OUTSIDE the plugin (`deep-research`, `find-docs`, built-in `Plan`/`Explore`).
- **Session indicator** — the copy-pasteable pointer to a recorded Claude Code session that `/dobby:mark` emits (transcript `.jsonl` path + repo, worktree root, the `STATE.md` path, the `/dobby:*` skills it invoked, and a note). Consumed by `/dobby:learn`, which digests that session to improve a kit skill from how it actually behaved in the field. Together `mark` (capture, in the consumer project) and `learn` (digest + edit, in this repo) are the kit's **self-improvement loop**; they couple to host paths (`~/.claude/projects`, `CLAUDE_CODE_SESSION_ID`) on purpose.
- **Teach** — the kit's on-demand pedagogy skill (`/dobby:teach`): the interactive Architect teaches the user ONE topic in-session — explains it from trusted resources, runs a tight feedback loop to verify understanding, and records the demonstrated understanding as evidence. It is conversational interaction, not planning or code work, so no worker is dispatched. It is NOT a work-session stage. Distinct from the `mark`/`learn` self-improvement loop, which evolves the kit rather than the user.
- **Capability** — a detected fact about a project, derived from signals in its dependencies/marker files (e.g. `vite`, `tanstack-start`, `react`, `neon`, `drizzle`, `react-email`, `vitest`, `expo`). Capabilities DRIVE the mechanical layer — `dobby` infers each task from them (the check pipeline, the `dev` composition, the `db:*` set, the capability-filtered help); see **Task inference**. `dobby env` reports the detected list; a capability is triggered by one or more **detection signals**.
- **Detection signal** — the concrete dependency or file that triggers a **capability** (e.g. `@tanstack/react-start` in deps → `tanstack-start`, `drizzle-orm`/`drizzle-kit` → `drizzle`); lives in code/tests, never printed.
- **Task inference** — the zero-config mapping (à la Vercel) from a project's detected **capabilities** to the commands `dobby` runs, REPLACING per-project config/scripts (no `run` key, no `package.json#scripts`, no vite-plus task table). Inferred: the check pipeline (Biome + tsc + knip, plus build-if-vite / test-if-vitest), the `dev` composition (portless-wrapped main → concurrent secondaries like react-email), the `db:*` task set (drizzle short names), and — per **Override by presence** — each tool's CONFIG itself (the capability-picked biome/vite/vitest/drizzle-kit preset), not just its command. Project-specific residue that resists inference lives in `dobby.config.json`'s `setup[]` / `teardown[]` / `checks[]` extras.
- **Override by presence** — the config model dobby applies to every tool it invokes (biome, knip, vitest, drizzle-kit, vite): dobby's shipped, capability-picked preset governs by DEFAULT whenever the consumer has NO config file for that tool; a consumer config file, when present, is a TOTAL override (never merged) — so a tool config file exists ONLY to carry a delta, and deleting it restores the default. A delta-less repo therefore carries only `package.json`, `tsconfig.json` (the one that always stays — `tsc` and vite's `resolve.tsconfigPaths` read it, and it holds per-project `paths`), and **dobby.config.json** (dobby's OWN contract, distinct from any tool config). External builders build THROUGH dobby (`bunx dobby build`), so dobby supplies the vite config there too. See [ADR-0015](./docs/adr/0015-configless-defaults.md).
- **Workroot** — the pinned working directory every `dobby` child process runs in: the git top-level, resolved ONCE per invocation (`git rev-parse --show-toplevel`) and pinned as the explicit `cwd` on every spawned tool, detached process, and cmux pane command (`cd <workroot> && …`, since cmux panes take no `--cwd`). A load-bearing invariant — it kills the run-in-the-wrong-checkout bug class. Action commands (`check`, `up`, `down`, `dev`, `db:*`, `update`) fail hard outside a git repo; only `env` degrades to null there.
- **Gate** — the single inferred quality pipeline `dobby check` runs: Biome + tsc + knip, the capability-gated build/test steps, then config `checks[]` extras. `dobby check --fix` is its pre-commit form. Two things now carry it mechanically: **`dobby ship`** — the ceremony command (stage → gate in-process → commit → push → PR), which is how `/dobby:commit` runs it — and the **pre-push backstop**, the `pre-push` hook `dobby up` installs, which re-runs the Gate (`dobby check --pre-push`, gate-cache short-circuit) so a red tree can never reach the remote. This supersedes the half of ADR-0013 that ruled out both a ceremony command and any git-hook enforcement — see [ADR-0017](./docs/adr/0017-mechanical-enforcement-of-the-gate-ship-and-the-pre-push-backstop.md); the release side is [ADR-0018](./docs/adr/0018-unified-release-by-adapters.md). _Avoid_: validate, quality checks.
- **ship** — the mechanized commit ceremony (`dobby ship`): stage → the **Gate** run IN-PROCESS with `--fix` → **gate cache** written → commit from the message file → push → `gh pr create` (only from a non-trunk branch, and only when the branch has no PR yet). **The exit code decides**: a red gate prints every finding WHOLE and commits nothing, and the caller never re-reads, re-runs, or re-interprets that output. The division of labour is fixed — `/dobby:commit` AUTHORS (doc-sync, the message, the PR body, whether to open one) and `ship` EXECUTES; the message and PR-body files are written OUTSIDE the repo, since ship stages the whole tree. _Avoid_: commit command, git ceremony.
- **gate cache** — the record at `.dobby/gate-cache.json` that lets an already-proven **Gate** be skipped instead of re-run. It holds TWO things: **ship**'s flat `{treeHash, dobbyVersion, configHash, exitCode, at}` record, which the **pre-push backstop** honors, and the green input sets — the last five **code hashes** a full green Gate cleared. `dobby check` itself now both READS and WRITES the second (a hit skips the inferred steps and says so: `gate skipped: inputs unchanged since last green (…)`; `--no-cache` skips the consult and runs everything), and **ship** delegates to it, since its own gate is an ordinary `check`. The key is COMPOSITE on purpose: a tree hash alone would serve a stale pass across a dobby upgrade or a `dobby.config.json` edit — both change what the Gate DOES to an unchanged tree — and only a green verdict is ever cached.
- **Inert set** — the fixed denylist of files no INFERRED **Gate** step consumes (Biome, tsc, knip, build, test), so editing one can never invalidate the **gate cache**: markdown (`**/*.md`) outside a fixture directory, the `docs/**` durable artifacts, and the host's `.claude/**`. It claims nothing about config `checks[]` extras — arbitrary consumer shell that may read anything, an inert file included (this repo's own frontmatter check reads `plugin/agents/*.md`) — which is precisely why the extras STILL run on a cache hit. Everything else counts as an input — `.gitignore`, `package.json` and the lockfile included, since they decide what the Gate sees and what it runs. Deliberately CLOSED and conservative: a file wrongly called inert buys a stale green. _Avoid_: ignore list, excluded files.
- **Code hash** — the **gate cache**'s per-run key: ONE uniform content hash of the whole non-**inert set** working tree (tracked ∪ untracked-but-unignored files, each path paired with its git blob oid, the pairs sorted then hashed), never a per-step key. It is taken AFTER the Gate's `--fix` pass, so it names the bytes the Gate is about to judge; it is index-neutral (it reads the tree, it never stages it); and it is null — run everything, cache nothing — whenever the tree cannot be enumerated, or holds an input git does not hand over as a plain file (a checked-out submodule, an embedded repository, any symlink: git enumerates the gitlink or the link itself and never what lies beneath it, so a key over the survivors would sit still while code the Gate reads changed). _Avoid_: tree hash (that is ship's flat record), fingerprint.
- **Edit hook** — the plugin's PostToolUse (`Edit|Write`) hook, which pipes each edited file through `dobby check --hook`: Biome's SAFE fixes applied in place, plus a whole-program `tsc` type check filtered down to the errors that land on the file just edited (TypeScript has no per-file mode, so the hook always runs it over the whole project and reports only what names this file); every guard a silent exit 0 (no config marker, no local bin, unsupported file…), exit 2 with findings on stderr only when something unfixable remains — so only unfixable findings ever reach the model. The implementor's own **Exit gate** later runs the full gate on the whole tree before handing the task to QA.
- **pre-push backstop** — the dobby-managed git `pre-push` hook that runs `dobby check --pre-push` over what is being pushed. It is ENFORCEMENT of the **Gate**, never a second gate: the same pipeline, with `fix=false` (a hook must never rewrite the bytes being pushed), and a tree **ship** already gated short-circuits through the **gate cache**. Installed idempotently by `dobby up`'s setup phase into the repository's COMMON hooks dir (one install covers every worktree); a `pre-push` hook dobby did not write is reported and left alone. Documented bypass: `git push --no-verify`. _Avoid_: pre-push gate, git-hook gate.
- **convention rules** — the EXECUTABLE tier of the **convention skills**: the house conventions a machine can decide without judgment, shipped as native Biome rules (in the react preset), the `conventions` **Gate** step (`conventions.ts` — the filesystem and cross-file facts no linter can see) and GritQL plugins (`cli/grit/*.grit` — the structural shapes Biome's native rules can't express). They fire at EDIT time through the **Edit hook** and at push through the **pre-push backstop**, so conformance no longer depends on a skill having been read. The remaining 17 judgment rules stay PROSE in the convention skills — a rule is mechanized only when a false positive is impossible. Every tier carries a per-site escape hatch for the deliberate exception: `// biome-ignore lint/<group>/<rule>` (native), `// biome-ignore lint/plugin/<grit-file-stem>` (GritQL), `// dobby-allow <RULE-ID>: <reason>` (the `conventions` step).
- **needsDecision** — the CLI's pause-for-human contract. A command that reaches a judgment a machine must not make alone EXITS nonzero having touched NOTHING, with a JSON payload naming the decision plus the context to decide it (`dobby release`: `{needsDecision: "first-release" | "0x-major", context: {currentVersion, commits}}`); the calling skill asks the user through an AskUserQuestion that restates that context and RE-INVOKES with the answering flag (`--bump <level>`). `release`'s `needsNotes` stop is the same shape for authorship. The CLI never prompts — it is non-interactive by contract, and the interactive coordinator owns the user judgment.
- **Canonical paths** — the fixed file locations dobby's **Task inference** imposes instead of per-project configuration (react-email templates live at `src/emails/`; the drizzle preset globs each module's co-located `src/**/schema.ts` / `schema.gen.ts` and writes migrations out at `./drizzle`); `/dobby:migrate-config` MOVES files there and rewrites imports rather than adding config knobs.
