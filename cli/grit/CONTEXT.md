# grit (tier-(c) convention rules)

The house stack's conventions that biome's NATIVE rules cannot express, shipped as
GritQL linter plugins — one `.grit` file per rule of the convention inventory. They
ride the REACT preset path only, so a non-stack consumer never sees a convention
about `@/shared`, TanStack or the `.server` boundary.

## Files

Each file is `c<NN>-<slug>.grit`, where `<NN>` is the inventory row id (`a2-…` for
the one rule DEMOTED out of tier (a) into this tier). Every file opens with
`engine biome(1.0)` + `language js(typescript,jsx)` and ends in a single
`register_diagnostic(span, message, severity = "error")`; none carries a rewrite, so
`dobby check --fix` never touches the code these rules flag.

- `c01-server-fn-outside-functions.grit` — a `createServerFn(…)` outside the module's `functions.ts`.
- `c04-eager-instance-outside-server-file.grit` — `betterAuth`/`drizzle`/`new Pool`/`new Resend`/`neonConfig` outside a `.server` file.
- `c05-lazy-server-instance.grit` — a `??=` MEMOIZING an eager server instance inside a `.server` file (PARTIAL — see Invariants).
- `c06-table-outside-schema-file.grit` — `pgTable`/`pgView`/`pgMaterializedView`/`pgEnum` outside `schema.ts`/`schema.gen.ts`.
- `c07-db-instance-without-schema.grit` — `drizzle({ client })` in `db.server.ts` with no aggregated `schema:`.
- `c09-collection-persistence-handlers.grit` — a collection carrying `onInsert`/`onUpdate`/`onDelete`.
- `c10-collection-not-eager.grit` — a `createCollection(…)` that is not an `export const` initializer.
- `c13-live-query-prop-set.grit` — a `<LiveQuery>` missing `fallback`/`query`/`retry`, or self-closing (no children render).
- `c14-retry-without-clear-error.grit` — a `<LiveQuery>` INLINE `retry` handler that never calls `.utils.clearError()` (PARTIAL — see Invariants).
- `c15-raw-live-query-hooks.grit` — a raw `useLiveQuery`/`useLiveSuspenseQuery` CALL outside `src/shared` (the call-site twin of the tier-(a) import ban A4).
- `c18-form-without-submit-validator.grit` — a `useAppForm({ … })` whose INLINE options carry no `validators.onSubmit` schema.
- `c19-field-control-without-render.grit` — a `field.Control` without its `render` prop.
- `c20-incomplete-field-anatomy.grit` — a `field.Root` missing Label / Control / ErrorMessage.
- `c21-dialog-form-not-rendered-as-form.grit` — a `form.Root` nested in `DialogContent`/`AlertDialogContent` children instead of its `render` prop.
- `c23-raw-value-submitted.grit` — an `onSubmit` handler awaiting a call with the raw `value` instead of a trimmed `data` payload.
- `c24-email-not-lowercased.grit` — an email-keyed payload property trimmed but not lowercased.
- `c25-hand-rolled-submit-button.grit` — a `<Button type="submit">` inside a `form.Root` subtree.
- `c26-secondary-button-outside-form-button.grit` — a `<Button type="button">` inside a `form.Root` subtree.
- `c27-manual-field-a11y-props.grit` — `aria-invalid`/`aria-describedby`/`htmlFor` hand-passed to a `field.*` component.
- `c29-test-reaches-into-form-internals.grit` — `form.state` reached in a test/spec file.
- `c31-barrel-module-import.grit` — a single-segment `@/module` import, in every specifier form it can take (PARTIAL — see Invariants).
- `c32-browser-value-import-of-server-module.grit` — an import of a `*.server` module inside a `*.browser` file that binds at least one VALUE specifier (the tier-(a) A9 fallback).
- `c33-zod-v3-email-validator.grit` — `z.string().email()` instead of zod v4's `z.email(…)`.
- `a2-import-meta-env.grit` — ad-hoc `import.meta.env`, outside the blessed out-of-Vite files.

## Interface

These files are **data, not code** — nothing imports them. Their only consumer is
biome, through the `plugins` array of `../biome/configless.react.jsonc`, which is
GENERATED by `../scripts/vendor-biome.ts` (the `GRIT_PLUGINS` list) and drift-gated
byte-for-byte by `../src/vendor-biome.test.ts`. A rule's PATH SCOPE lives in that
list (`includes` globs), never in the pattern: a GritQL pattern sees a file's syntax,
never its location. Behavior is pinned by `../src/grit-rules.test.ts`, which runs the
real gate over throwaway repos.

## Invariants

- **Declared in the config-less wrapper, never in `react.jsonc`.** Biome resolves a
  plugin path relative to the ROOT config — the file `--config-path` names, or the
  consumer's own `biome.jsonc` — NOT relative to the config that declares it. From
  `configless.react.jsonc` the `../grit/…` paths land inside dobby's package and the
  rules fire; declared in `react.jsonc` the same paths would be resolved from a
  CONSUMER's project root, miss, and abort their ENTIRE biome run with
  `Error(s) during loading of plugins: Cannot read file`. Lab-verified, bundled biome
  2.5.4. A consumer who ships their own `biome.jsonc` therefore opts in by declaring
  the plugins themselves (see `cli/README.md`).
- **No escaped double quote in a message.** GritQL's string unescaper mangles the
  REST of a string after a `\"` (downstream `r`/`t`/`n` letters come out as CR/TAB/LF
  in the emitted diagnostic). Every message here quotes with apostrophes.
- **Every path-scoping glob is `**/`-prefixed**, like the react preset's override
  globs: under `--config-path` biome anchors them to the config's own directory, not
  the project cwd.
- **No capturing group in a regex.** `r"…(a|b)…"` makes the engine expect a bound
  metavariable and the plugin errors at match time; use `(?:a|b)`. Regexes are
  ANCHORED (full-match): `r"server"` matches nothing inside `"./x.server"`.
- **`import $clause from $source` is broad ACROSS clause kinds and narrow WITHIN
  one.** It matches the default, named and `import type` clause forms alike — but
  inside a named clause it only matches a SINGLE specifier: lab-probed against
  bundled biome 2.5.4, neither `import { a, b } from "…"` nor the combined
  `import def, { a } from "…"` matches it at all. NO import rule here rides that
  snippet any more. Both match `JsImport()`, test the `JsModuleSource()` they
  contain, and then ENUMERATE the specifier nodes (`JsDefaultImportSpecifier` /
  `JsNamespaceImportSpecifier` / `JsShorthandNamedImportSpecifier` /
  `JsNamedImportSpecifier`): c32 asks whether any one of them binds a VALUE (it must
  spare type imports yet catch the mixed `{ type A, b }` form), c31 only that the
  statement binds SOMETHING — a barrel is a barrel whether the names are types or
  values, so it needs no per-specifier predicate and therefore no `bubble` (probed
  both ways: identical output). Each file's header pins its own verdict table. The
  shared consequence of enumerating: a BARE side-effect import binds no specifier
  and is out of reach of both — as it was under the snippet.
- **A type qualifier is a TOKEN, so it is read as text.** `import type { A }` puts
  the qualifier on the CLAUSE (each specifier's own text stays bare) while
  `import { type A }` puts it on the SPECIFIER; CST patterns expose no token fields,
  so c32 needs BOTH tests — the clause-level `not … r"import\s+type…"` guard and an
  anchored per-specifier `not … r"type\s…"`.
- **The assets are formatted by the bundled biome.** `.grit` sits inside biome's
  format surface, so these files answer to the repo's own gate and are kept
  formatter-clean (`biome check cli/grit` exits 0): two-space indent, and
  `register_diagnostic(span=…, message=…, severity=…)` collapsed onto ONE line. That
  formatting is semantically inert — verified by re-running `../src/grit-rules.test.ts`
  and re-probing c1/c4/c31/c32/c33/a2 through `dobby check --lint` over a scratch repo
  before and after — so an edit that re-wraps a call gets re-formatted, never exempted.
- **Severity is `error`** on every rule, because `dobby check` counts only
  `error`/`warning` diagnostics — an `info` rule would be invisible to the gate.
- **A rule matches the CONSTRUCT, never a lookalike.** At `error` severity a false
  positive turns the gate red on conformant code, so a rule that cannot see the
  whole construct SHRINKS rather than approximates: c14 matches the `retry` prop of
  a `<LiveQuery>` element (not any component's `retry`) and only an INLINE handler;
  c05 requires the `??=` right-hand side to construct one of C4's eager instances
  (not any `??=` in a `.server` file); c18 only reads an INLINE options object. The
  half a single-file pattern cannot decide is parked in the file header WITH the
  falsifying fixture, never shipped as a looser pattern.
- **Handler/argument SHAPES are matched by CST node kind, not by snippets.** A
  snippet like `function $name($params) $body` does not match a zero-parameter
  handler (lab-verified: `retry={function retryTasks() { … }}` slipped through);
  `JsArrowFunctionExpression()` / `JsFunctionExpression()` / `JsObjectExpression()`
  / `JsSpread()` cover every form of their construct.

## What's intentionally NOT here

Rules attempted and PARKED, with the evidence (the falsifying fact), so nobody
re-litigates them from scratch:

- **C2 / C3 / C12 — cross-file.** GritQL plugins are single-file. C12 compares a
  collection's `.pick({…})` with the sibling `functions.ts` `.select({…})`; C2 must
  resolve a middleware reference across files; C3 must decide whether a
  `createServerFn` chain's `.middleware([…])` resolves to `requireAuth`. C3 carries a
  SECOND blocker: the convention is "any SESSION-REQUIRING server fn", and a login /
  signup endpoint is legitimately public — an unconditional presence check would flag
  exactly the code that must stay unguarded. Belongs in a tier-(b) CLI check.
- **C8 — a template file missing `export const subject` / the arrow `Email` /
  `export default Object.assign(…)`.** It is an ABSENCE assertion over a whole file;
  GritQL registers diagnostics on matched NODES, and there is no node standing for
  "this module lacks X". Belongs in a tier-(b) CLI check.
- **C11 — a timestamp column without `z.coerce.date()`.** Deciding which columns are
  timestamps requires the drizzle table in the sibling `schema.ts` — cross-file. A
  single-file approximation (flag `createSelectSchema` with no overrides) would fire
  on every schema that legitimately has no timestamp column.
- **C16 — a project-local factory wrapping `createCollection`.** "Wrapped in a
  factory" has no distinguishing shape beyond "not an `export const` initializer",
  which C10 already reports; anything broader flags legitimate helpers.
- **C17 — a `<LiveQuery>` children callback with no `rows.length === 0` branch.**
  The inventory itself marks it LOW CONFIDENCE: the single-derived-value form the
  skill blesses has no list to be empty, so the rule would false-positive on the
  documented pattern.
- **C22 / C28 — dialog `form.reset()` on close, and the submitting lock.** Both would
  fire on any dialog form with no `onOpenChange` at all, including the authored
  `archive-dialog` fixture, and inventory row N14 (forms that persist on the page must
  NOT reset) is the exception that makes the shape unsound when over-applied.
- **C30 — a mutation with no `toast.success`/`toast.error`.** The inventory marks it
  HEURISTIC: nothing syntactic separates "a mutation" from any other async function.
- **C34 — a `query` prop that can return `undefined`.** "Can return undefined" is a
  dataflow property, not a shape.
- **A11 — a query-source alias shadowing a route-scope binding.** Needs scope
  resolution (which binding does this name shadow?); GritQL matches syntax, not
  scopes. Native `noShadow` covers it only as a blanket superset — the reason it was
  demoted here in the first place.
- **The intra-module half of C31**, **the cached-`getX()` half of C5**, and **the
  HOISTED-handler half of C14** (`retry={retryTasks}` with the function declared
  elsewhere in the file — resolving the identifier is a scope question, and the naive
  "does the file mention clearError" approximation was lab-shown to flag conformant
  code) — see the PARTIAL notes in those files. C18 reads only an INLINE options
  object for the same reason.

No rule ships a REWRITE (`=>`). Every diagnostic here names the house alternative;
applying it is a judgment call, and an unsafe autofix on convention code is not worth
the blast radius.
