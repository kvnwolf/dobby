# cli (`@kvnwolf/dobby`)

The `dobby` CLI: the kit's mechanical execution layer. Run it from a project to
snapshot the working environment (`dobby env`) — worktree, cmux, capabilities,
config — and to read the per-topic instruction catalogue for the detected
environment (`dobby instructions <topic>`), with every fact resolved locally
(no network). Worker model/effort lives solely in each agent's own frontmatter
under `plugin/agents/`; this CLI carries no worker-consumption recipe.

## Files

- `src/index.ts` — the bin adapter (shebang `#!/usr/bin/env bun`). Logic-free EXCEPT two concessions. (1) The **streaming split**: a CLEAN live `dobby dev` (the `dev` positional with NO flags — decided by the PURE `tasks.isLiveDev`, which lives there precisely because this file is never an import target) is intercepted here and handed to `lifecycle.runDev` — it manages a concurrent process group (portless-wrapped main + secondaries) with signal forwarding and lives until the group exits, which the synchronous capture seam (`run()`) cannot supervise; everything else — every finite command, `dev --dry-run`, AND any FLAGGED dev — routes through `run()` unchanged, so its strict `parseArgs` stays the SINGLE flag validator (an unknown flag such as `--no-share` exits 1 + usage instead of being silently swallowed by the stream). (2) When `--hook`, `--pre-push` or `--stdin` is in argv it drains `process.stdin` (the PostToolUse payload / git's pre-push ref lines / a `state` body) and threads it as `run()`'s third argument — the drain condition MUST list every stdin-consuming flag: a `--pre-push` missing from it would leave the backstop reading nothing and waving every push through, which no in-process test can catch. Otherwise reads only `process.argv`/`process.cwd()`, calls `run()`, writes stdout/stderr, exits. Not an import target, not unit-tested.
- `src/run.ts` — **the module's interface**, `run(argv, cwd, stdin?)`. Parses argv (`node:util` `parseArgs`, strict), dispatches on the first positional, and formats output (all `key: value` / JSON rendering lives here, incl. the db/dev/up/down dry-run plans — `up`'s plan renders the folded setup phase first — AND the capability-filtered usage/help). Returns the process outcome as data. `stdin` carries the `check --hook` payload, the `check --pre-push` ref lines (dispatched to `hook-install.ts`'s `prePushCheck`) and the `--stdin` commands' body; every other command ignores it. For `dev` it PLANS only — `run()` is the capture seam, so it renders the `--dry-run` plan and enforces the no-app gate ('nothing to run'); the LIVE dev group is owned by index.ts's streaming path (which intercepts a CLEAN, flagless `dobby dev` before `run()`; a FLAGGED dev always reaches `run()` and its strict parse), so `run()` never spawns a dev server. The usage text is COMPUTED per invocation: `buildUsage(detectCapabilities(cwd))` (the SAME detection over the passed cwd that `env`'s `capabilities:` line uses) lays out `tasks.usageCommands` into the aligned Commands block; the Options block is static. Every usage-printing path (bare, parse error, unknown command) uses this filtered text.
- `src/command.ts` — the CONTRACT between `run.ts` (dispatcher + renderer) and the DOMAIN modules that own one session command each (`ship`, `release`, `state`, …): `CommandOptions` (only the flags actually present, already validated against that command's allowlist), `CommandContext` (`command`, `cwd`, `options`, `positionals` — `[0]` is the already-validated subcommand — and the optional `stdin`), `CommandResult` (`exitCode` + optional `json` / `text` / `error`) and `notImplemented(command)`. Deliberately IMPORT-FREE — every domain module depends on it, so it must never pull in the CLI's I/O surface — and the rendering it implies is GENERIC (a `json` payload prints as ONE `JSON.stringify` line, else `text` verbatim, `error` to stderr), which is what lets a task fill a module WITHOUT editing the dispatcher (spec Decision 19: parallel tasks never co-edit `run.ts`). A domain module never reads `process.cwd()`/`process.argv` itself, so the in-process `run(argv, cwd, stdin)` seam reaches every command.
- `src/detect.ts` — internal capability detector. `detectCapabilities(root)` reads `<root>/package.json` (dependencies ∪ devDependencies) and returns the capability names in fixed catalog order. TOLERANT: a missing/unparseable package.json contributes no signals (never throws). Single-package only.
- `src/config.ts` — the SOLE reader of project Dobby JSON config. `loadConfig(root)` is tolerant: `null` when the file is absent, `{ ok: false, error }` when unparseable/invalid, `{ ok: true, config }` when valid. `DobbyConfig` includes `files[]`, optional setup/teardown/check extras, and tracker/release. Worker model/effort deliberately does not belong in this project contract — that lives solely in each agent's own frontmatter under `plugin/agents/`.
- `src/runner.ts` — the shared workroot-pinned child-process utility (every command's single spawn seam) AND the single bin resolver. `resolveWorkroot(cwd)` finds the git top-level (null outside a repo — the ONE call that reads the ambient cwd); `requireWorkroot(cwd)` is its fail-hard variant for action commands. `resolveBin(name, { scope, root? })` is THE resolver every dobby TOOL spawn routes through: `scope: "bundled"` (portless, biome, tsc, knip, taze) resolves from DOBBY's OWN tree — walk `node_modules/.bin/<name>` upward from this module's location (`import.meta.url`; handles nested + hoisted layouts), then a `require.resolve` fallback on the shipping package's `bin` field, then the bare name — so bundled tools resolve PATH-INDEPENDENTLY (the field-bug fix: `env` spawned a BARE `portless` off PATH and got `devUrl: null`); `scope: "consumer"` (vite, vitest, drizzle-kit, email) resolves `<root>/node_modules/.bin/<name>` first, else the bare name. In both scopes PATH is only a last-resort fallback. System tools (git, curl, cmux, sh, bunx, gh, npm, bun) stay BARE and never call it — `gh`/`npm`/`bun` joined with `ship`/`review`/`release`, and the release ones stay bare ON PURPOSE: a publish runs against the USER's own npm auth (`~/.npmrc`), so it must be the same `npm` their shell would run, never one resolved out of dobby's tree. **`resolveAsset(relPath)`** is the ASSET counterpart to resolveBin's bundled scope — it resolves a SHIPPED preset (`biome/core.jsonc`, `knip.base.jsonc`, `vitest.base.mjs`, …) to an absolute path inside dobby's OWN package tree (walked from `import.meta.url`: the runner is always at `<pkgRoot>/src/runner.ts`, so `<pkgRoot>` is its grandparent), and **`configArgs(root, spec)`** is the config-less-defaults seam (ADR-0015): given a tool's pure `ConfigDefaultSpec` (from tasks.ts), it returns the config args to APPEND to the tool spawn — NO args when the consumer ships its OWN config at `root` (a matching file, or knip's `package.json#knip` key → bare spawn, native discovery, a TOTAL override) else the tool's native config flag pointing at `resolveAsset(spec.asset)` (biome additionally gets `--vcs-root=<root>` — the ultracite preset sets `vcs.useIgnoreFile: true`, so an explicit vcs-root at the workroot stops biome resolving the ignore file beside the preset and erroring), plus a note label (`usedDefault`). `runCapture`/`runInherit` spawn (synchronously) with `cwd` pinned to the passed `root` (never ambient), returning data (never throwing). `spawnDetached(cmd, args, { root })` is the ASYNC streaming counterpart: it `spawn`s a long-running child DETACHED (its own process group) with inherited stdio, cwd pinned, and returns the live `ChildProcess` so the caller manages the GROUP as a unit (wait for exit, forward signals, `process.kill(-pid)` to tear the whole group down) — consumed by the `dev` executor. `spawnBackground` (the detached-with-a-log-file spawn `up`'s plain-terminal start used to call directly) is GONE — the model now runs `start`'s instruction text itself (a background `Bash` job under terminal, a cmux `send` under cmux), and `dobby dev` registers its OWN pidfile on startup (`pidfile.ts`'s `writePidfile`), so nothing in this file spawns the run anymore. `node:child_process` `spawnSync`/`spawn` only (never Bun.spawn).
- `src/pidfile.ts` (+ `src/pidfile.test.ts`) — the RUN-PROCESS REGISTRY. Owns `<workroot>/.dobby/dev.pid`: `writePidfile` (called by `dobby dev`'s streaming path on startup), `liveRegisteredPid` (the live-AND-owned pid check `planDev` consults to refuse a live twin, and `up` consults to find an in-flight start to wait out instead of handing back another `start` instruction), `clearOwnPidfile` (self-teardown, only when the file still names THIS process), and `killFromPidfile` (`down`'s teardown — SIGTERM the bare `pid`, never the process group, since a model-launched `dobby dev` is not guaranteed to lead one; ownership requires BOTH the `ps` command-line `dobby dev` signature AND a start-time match within a 15s tolerance, closing the pid-reuse hole a signature check alone would leave — a mismatch removes the file silently and signals nothing). Sits BELOW both `environment.ts` and `lifecycle.ts` in the import graph (imports neither), so both may import it without ever risking a cycle.
- `src/browser-guide.ts` (+ `vendor/cmux-browser/` — `SKILL.md`, `commands.md`, `PROVENANCE.md`) — the two UI-verification protocol VARIANTS the `browser` topic answers with (`CMUX_GUIDE`, `NON_CMUX_GUIDE`), consumed by the adapters' own `instruction()` — never by `env` directly anymore. `CMUX_GUIDE` is the vendored cmux-browser protocol (Rung 1 of the ladder — open, read the URL, snapshot for fresh refs, act, wait, re-snapshot, stale-ref and script-error recovery), read once at import time from `vendor/cmux-browser/{SKILL.md,commands.md}` — vendored UNMODIFIED from `manaflow-ai/cmux`, never fetched live (irreproducible, network-dependent); `adapters/cmux.ts`'s `browser` catalogue entry answers it verbatim. `NON_CMUX_GUIDE` is the non-cmux ladder (Rung 2 claude-in-chrome falling back to Rung 3 curl-only); `adapters/terminal.ts`'s `browser` entry answers it verbatim, and `adapters/claude-desktop.ts` / `adapters/t3-code.ts` answer their OWN hand-written guides instead (over the Claude Browser MCP server / the `mcp__t3-code__preview_*` tools respectively — see `adapters/*.ts` below), never this file's variants. Provenance (repository, commit, licence, per-file SHA-256) recorded in `vendor/cmux-browser/PROVENANCE.md` the way `plugin/skills/trim-context/scripts/vendor/PROVENANCE.md` already records the vendored Tree-sitter runtime (ADR-0027). Both variants are deterministic module-level constants — no network of its own, on every call.
- `src/environment.ts` — the **ENVIRONMENT ADAPTER SEAM** (issue #27), now DETECTION + INSTRUCTION CATALOGUE only. One flat file (no barrel, no subdirectory — `src` stays one-file-per-role): the `Environment` interface (`id`, `cmux`, `discoverPanes`, `instruction(topic, context)`), the `Topic` union (`start` | `stop` | `browser` | `rename` — the four things dobby cannot act on the model's behalf for), the `Instruction` shape (`{applies, text, topic}` — `applies: false` carries `text: ""`, the CALLER owns the not-applicable rendering), `SurfaceContext`/`PaneRefs`, and `detectEnvironment()`. Detection is a FOUR-RUNG cascade, read ONCE per invocation (never memoized — tests toggle env vars between cases): `CMUX_WORKSPACE_ID` present -> `cmuxEnvironment()`; else `CLAUDE_CODE_ENTRYPOINT` one of Claude Desktop's three documented values (`claude-desktop`, `claude-desktop-3p`, `local-agent` — `code.claude.com/docs/en/monitoring-usage`) -> `claudeDesktopEnvironment()`; else `__CFBundleIdentifier` starts with the t3-code bundle prefix -> `t3CodeEnvironment()`; else `terminalEnvironment()` (the floor — an unknown SDK host lands here, and its instructions work anywhere). `up` no longer executes anything through this interface beyond pane DISCOVERY (so a `start`/`stop`/`browser` instruction's text can embed a discovered surface ref) — starting, stopping, renaming and opening surfaces are now instructions the MODEL carries out itself, printed by `dobby instructions <topic>` and embedded in `up`/`down`'s `instructions[]`. The four real implementations live one-file-each under `adapters/` (see below). `environment.ts` must NEVER import `lifecycle.ts` (lifecycle.ts imports THIS file); `pidfile.ts` sits below both. What stays OUT of this seam, in `lifecycle.ts`: portless, the liveness probe, Neon branch provisioning, and the `up`/`down` plan-rendering data (`UpAction`/`DownAction`/`UpPlan`/`DownPlan`) — none of that varies by host runner.
- `src/adapters/{cmux,terminal,claude-desktop,t3-code}.ts` — the four `Environment` implementations, one file each, no barrel. **`cmux.ts`** discovers panes via `list-panes` + `list-pane-surfaces` (tolerant parsing — the cmux stdout ref format is runtime-unverified) and answers a catalogue where every topic applies: `start` reuses a discovered run pane (`cmux send`) or instructs creating + naming one, `stop` names `cmux close-surface` for each discovered kit pane (applies only when one exists), `browser` prepends a surface step to `CMUX_GUIDE`, `rename` names `cmux rename-workspace` with the slug unquoted. **`terminal.ts`** is a REAL second implementation, not "cmux with no-ops": `start` instructs a background `Bash` job (`run_in_background`) running `bunx dobby dev`, `browser` answers `NON_CMUX_GUIDE`, and `stop`/`rename` never apply (`dobby down` kills the registered process itself; a plain terminal has no workspace to rename). **`claude-desktop.ts`** (detected via `CLAUDE_CODE_ENTRYPOINT`, cross-platform) and **`t3-code.ts`** (detected via the macOS-only `__CFBundleIdentifier` prefix — t3 code on Linux/Windows falls through to `terminal.ts`) each DELEGATE `start`/`stop`/`rename` to `terminalEnvironment()`'s own answers verbatim (no run/rename surface of their own) and answer their OWN hand-written `browser` guide: Claude Desktop's over the built-in `Claude Browser` MCP server (`mcp__Claude_Browser__*`, aliased `Claude Preview`), UNVERIFIED against a live Desktop — written from a field study dated 2026-08-19 (Claude Desktop 1.30096.5, Claude Code 2.1.229), `docs/field-studies/claude-desktop-2026-08-19.md`, with the marker restated in the guide text itself so replacing it is visible; t3 code's over the vendor's `mcp__t3-code__preview_*` tool family, VERIFIED against t3 code v0.0.38 on 2026-09-02 (tool schemas loaded live; source `pingdotgg/t3code`). None of the four adapters spawns the run itself anymore — that is the model's job, carried out from the `start` instruction's text.
- `src/envinfo.ts` — env-snapshot assembly. `collectEnv(root)` returns the `EnvSnapshot` data — `branch`, `browserPane`, `capabilities`, `cmux`, `config`, `dbTasks`, `devUrl`, `runPane`, `worktree` (nine keys, no UI-verification field — `dobby instructions browser` answers that now); `dbTasks` are the INFERRED `db:*` names read from the SAME pure `tasks.dbTasks` map the executor resolves through, and `cmux` / `browserPane` / `runPane` are read straight off the ONE `Environment` `environment.ts`'s `detectEnvironment()` resolves for this call — the pane-discovery mechanics and the environment-detection reads live there now, not here. It resolves the workroot ONCE via `runner.ts` and pins every git/portless spawn to it. Every fact degrades to null/false/[] and `env` never throws; there is no worker-consumption recipe here to expose (that lives solely in each agent's own frontmatter under `plugin/agents/`). `resolveDevUrl` is EXPORTED and reused by lifecycle (portless resolution is environment-agnostic, so it stays here rather than crossing the adapter seam).
- `src/tasks.ts` — PURE task inference (no spawning, no fs, no process — the most-tested module). `checkPipeline(capabilities, config, flags)` returns the ORDERED `CheckStep[]` plan for `dobby check`: full gate (no flags) = biome, tsc, knip, the capability-gated build (needs `vite`), the stack-gated **conventions** step, the capability-gated test (needs `vitest`), then config `checks[]` extras — conventions sits AFTER build on purpose, because its B8 rule scans the built client bundle and an earlier placement would judge the PREVIOUS run's output; selective flags (`lint`/`types`/`unused`/`build`/`test`) pick a SUBSET of the tool steps in that same order and drop the extras. Capability gating is decided HERE: a build/test step whose capability is absent still appears in the plan but carries a `skipNote` (the single line `check.ts` prints). The `conventions` step is the exception on both counts — `conventionsEnabled(capabilities)` (exported, `react` or `tanstack-start`, the SAME fork the tier-(a) biome preset and the tier-(c) GritQL plugins ride) makes it simply ABSENT for a non-stack repo (nothing was skipped — the conventions never applied), and it has no selective flag of its own, so it runs on the FULL gate only. `check.ts` executes the plan (and calls `conventionsEnabled` directly on the two paths that bypass it — the per-file fast path and the edit hook — so the gate cannot disagree with itself about who is a stack consumer). `dbTasks(capabilities)` returns the inferred `db:*` map (a `DbTaskSet`: `mode` = none/single + a name→`DbCommand` map): drizzle is the ONLY db tool, so the SHORT names always map to drizzle-kit (`db:push` → `drizzle-kit push`, etc.); no drizzle → an empty set (mode "none"). `UPDATE_ARGS` is the pure `taze --interactive` arg vector. `devPlan(capabilities, config)` returns the ordered `DevPlan` for `dobby dev`: `main` (null with no vite → the no-app gate; else the `.vite` cache-clears + the `vite dev` command that lifecycle wraps in `portless run`) and concurrent `secondaries` (`email dev --dir src/emails` for react-email — the canonical emails dir, the only secondary). `config` is threaded for forward-compat (v1 has no config-driven dev behavior). `lifecycle.ts` executes them. `isLiveDev(argv)` is the bin's STREAMING-SPLIT predicate — true ONLY for a clean live dev (the `dev` positional with NO flag token), so every flagged argv falls through to `run()`'s strict parse (kept pure HERE because index.ts is not unit-testable). `usageCommands(capabilities)` returns the capability-FILTERED `dobby` help Commands list (`UsageCommand[]` — name + one-line description): the universal set (env/instructions/check/update) always, dev/up/down/**build** ONLY with `vite` (`up` described as the prepare + probe entry point; `build` the inferred Vercel buildCommand), and the `db:*` entries ONLY with a db capability — each carrying its ACTUAL resolved name (from `dbTasks`) and the concrete shell command it runs. `run.ts` renders it (the field-report fix — the help no longer advertises commands the repo can't run). The **config-less-default specs** (ADR-0015) also live here (pure): `biomeConfigSpec`/`vitestConfigSpec`/`viteConfigSpec` (capability-driven — react → the react preset, tanstack-start → the tanstack vite preset — but the two MULTI-IMPORT presets also take the dependency set and pick the variant only when ALL of its imported packages are declared; `vitestConfigSpec` DEGRADES to the import-safe base when one is missing, while `viteConfigSpec` FAILS LOUD — it returns a discriminated `ViteConfigSelection` (`{ kind: "default"; spec } | { kind: "blocked"; missing }`), the `blocked` variant firing for a config-less tanstack app missing any import so callers HARD-ERROR instead of silently serving a pluginless base), `knipConfigSpec`, `drizzleConfigSpec` — each (except vite's `blocked` branch) a `ConfigDefaultSpec` (own-config filenames + optional `package.json` key, the tool's native flag + `--flag=value` form, the shipped asset relpath, the note label). `viteBlockedMessage(missing)` is the pure shared error text (missing packages + both remedies). The DECISION is pure here; `runner.configArgs` does the impure fs presence check + `resolveAsset` at spawn time, and `runner.resolveViteConfig` combines that presence check with the block enforcement (a present consumer config overrides the block).
- `src/check.ts` — the quality-gate EXECUTOR of the `tasks.ts` plan. `check(files, cwd, flags, fix?, noCache?, baselineRecord?)` shells out to the tools (never an in-process/WASM API) and returns findings + notes as DATA (`run.ts` formats). `fix` (the `--fix` flag) applies biome's SAFE fixes FIRST — project-wide `biome check --write .` (reaching the config files too, not just `src/`), or over just the named files on the per-file path — so the pre-commit gate never fails on formatting the edit hook did not reach; the UNSAFE rewrites (e.g. `==`→`===`) are NEVER applied. It then runs the selected pipeline and reports whatever biome could NOT safely fix. `checkHook(stdin, cwd)` is the edit-time PostToolUse path: it parses the hook payload's `tool_input.file_path` defensively, runs `biome check --write` (SAFE fixes) on that one file so formatting is fixed in place, ALSO scans it for tier-(b) convention violations when the repo is a stack consumer (never fixable — no convention rule ships a rewrite), and returns `{ surface: false }` for every guard (unparsable payload / no file_path / missing file / not a git repo / no `dobby.config.json` marker / file outside the workroot / extension outside `ts,tsx,js,jsx,json,jsonc,css` / biome could not run / biome fixed everything and no convention broke) or `{ surface: true, groups }` when unfixable findings remain (run.ts prints them to STDERR and exits 2). Per-file (file args): biome over those files PLUS — for a stack consumer — the tier-(b) convention rules that judge those same files (`conventions.ts` in per-file mode); the edit-adjacent fast path, no pipeline/flags. Project-wide (no file args): runs the `checkPipeline` plan — `biome check --reporter=json .` + `tsc --noEmit --pretty false` + `knip --reporter json`, plus (when the gating capability is present) `vite build` / `vitest run --reporter=json`, and — BETWEEN those two, so its bundle rule reads the build this run just wrote — the in-process **conventions** scan (the one step that does not shell out: its findings are adapted into the same `CheckGroup` shape by `conventionsGroup`, so the gate's exit code, the report grouping and the hook's exit-2 contract carry them unchanged, and its notes are ordinary step notes), then config `checks[]` shell extras (`sh -c`, run last, fail-fast among themselves). **Config-less defaults (ADR-0015):** every tool ONLY dobby invokes — biome (project-wide, per-file, `--fix` pre-pass, AND `checkHook`), knip, the build (vite) + test (vitest) steps — gains its native config flag pointing at dobby's SHIPPED preset via `runner.configArgs` WHEN the consumer ships no config of its own (else bare — a total override). tsc is NOT in this set (the one config that always stays is the consumer's `tsconfig.json`). When ANY default was active the run emits ONE token-lean note — `configs: biome=default(react) · knip=default · vitest=default` — omitted entirely when every tool used a consumer config; the per-file fast path stays note-free (edit-adjacent) but still uses the default. BUNDLED bins (biome/tsc/knip) resolve from DOBBY's OWN node_modules; the capability-gated vite/vitest bins resolve from the CONSUMER's node_modules (a bundled second vite would clash with the consumer's plugins). Bin lookup reads each package's `bin` field (`binFrom`); knip's `exports` blocks the `./package.json` subpath, so its root is found by walking up from the resolved main entry (`pkgRootFrom`). knip is TOLERANT — a run that can't start (no package.json) folds to zero findings, never a hard error. Biome findings count only `error`/`warning` severities; tsc lines parse via `path(line,col): error TSxxxx: message`. Biome diagnostics inside **dobby's own state dir (`.dobby/`)** are DROPPED (and a biome exit 1 caused by nothing else is normalized to 0, so the gate doesn't read it as a crash): that dir holds files dobby itself writes (`gate-cache.json`, `dev.pid`, …), so dobby's bookkeeping can never fail the consumer's gate — the presets' `!.dobby` ignore only reaches the config-less REACT mode (a consumer's own biome config and the config-less CORE preset, which biome loads as a NESTED config and whose `files` settings it therefore ignores, both lint it). The vitest step runs under NODE when a usable node exists (a cheap `node --version` probe via `runCapture` — node stays BARE, never `resolveBin`'d), falling back to `process.execPath` otherwise: under `bunx dobby`, `process.execPath` is bun, and vitest-under-bun's module runner mis-resolves some deps' dual export maps (field bug: zod v4's `z.enum` → undefined), so pinning the vitest spawn to node makes the gate deterministic by invocation; ONLY the vitest spawn is affected (build/tsc/biome/knip are unchanged), and the fallback-runtime failure note names the runtime so a bun-runtime failure is diagnosable. **Findingless-failure diagnosability**: when a tool STEP exits nonzero but contributed ZERO parsed findings (the crashed-tool case — a startup/config error, not lint findings), the step's note (`<tool>: failed (exit N)`) carries a `raw` field — a clearly-labeled tail of the child's stderr (falling back to stdout when stderr is blank), capped to the last ~40 lines then ~4KB (whichever is smaller) to stay token-lean; `run.ts` renders that tail under the note line. This applies to the BUILD step (which never produces findings, so ANY nonzero exit is findingless) and to biome/tsc (a nonzero exit with zero error/warning findings = a crash, via `findingsStepCode`); findings-producing failures (biome/tsc findings) are UNCHANGED (no tail). **The TEST step is now the exception (A1)**: on a nonzero vitest exit `check` PARSES the captured `--reporter=json` stdout (`parseVitestFailures`, pure + private — reached in CI through a STUB vitest bin that exits nonzero with hand-written reporter JSON, never a real vitest run — the same stub-bin seam the A2 tests use to make the step spawn) into a REAL summary rather than a raw tail — one line per failed test FILE (`<repo-relative file> — <first message/failureMessage line>` + the first in-repo stack frame `(file:line)` when present, covering BOTH file-level LOAD failures and individual failed tests), capped at ~10 files with a `…N more` tail, under a `test: N suite(s) failed — <first file>` header note (the field fix: a suite that fails to LOAD appears EARLY in the JSON, so the old raw TAIL truncated it out behind a wall of passing tests). The raw JSON TAIL survives ONLY when the JSON can't be parsed at all / carries no failed suite (vitest died before reporting). **Hermeticity note (A2)**: `check` appends this advisory ONLY when the vitest step ACTUALLY SPAWNS (bin resolved — a missing consumer bin degrades/skips WITHOUT running vitest, so nothing is advised) AND the SELECTED config is dobby's react default (`vitest.react.mjs`, the ONLY preset that calls `loadEnv` — a base preset or a consumer-owned vitest config is silent, their env contract not dobby's to judge; the gate is `configArgs`'s `usedDefault === "default(react)"`). When both hold it compares env-file KEY SETS ONLY (never values): a workroot `.env.local` with NO `.env.test` → the inherits note (`test: vitest inherits .env.local (absent in CI) — commit a placeholder .env.test for hermetic runs`); BOTH files present → an INCOMPLETE `.env.test` (keys in `.env.local` absent from `.env.test`) → `test: .env.test is missing N key(s) present in .env.local: A, B, … — CI runs without them` (names capped at ~6, then `…N more`); a complete superset, or no `.env.local`, is silent. **knip is the deliberate exception** — its can't-start crash folds to zero findings and never fails the gate (the tolerance invariant), so it never reaches the findingless-failure path; config `checks[]` extras are likewise unchanged. ALL selected steps run (report everything); the report's `exitCode` is the FIRST failing step's code. **GATE CACHE (per-check)**: the project-wide path is wired to `gate-cache.ts` (the sole owner of `.dobby/gate-cache.json` — check.ts never hashes/reads/writes it itself). The CODE HASH is computed ONCE per run, AFTER the project-wide `--fix` pass (which rewrites the tree) and after the capability scan, so the key names the bytes this gate is about to judge. A HIT (`consultGreenInputs`: this exact input set already cleared a FULL gate under this dobby + this `dobby.config.json`) SKIPS the six inferred steps and emits `gate skipped: inputs unchanged since last green (<short-hash> @ <at>)` as an ordinary note — but the config `checks[]` extras STILL run (an extra is arbitrary shell that may read files the hash deliberately does not cover) and THEIR verdict is the exit code. A green FULL gate that actually ran calls `recordGreenInput` (a write failure is a NOTE, never a verdict). SELECTIVE flags consult (a full-green hit proves any subset) but NEVER record; the per-file fast path and `checkHook` never touch the cache at all; `noCache` skips the CONSULT but still records a full-gate green (turbo `--force`); a null code hash (not a git repo, an unenumerable tree) simply runs everything, records nothing and says nothing. Returns `{ ok: false, error }` (not a git repo / a BUNDLED tool unresolvable) or `{ ok: true, groups, notes, exitCode, gateCached }` (notes are `CheckNote`s — `text` + optional crashed-tool `raw` tail; `gateCached` is that skip-note line on a hit and null otherwise — the same line also travels in `notes`, so the field exists for callers that COMPOSE `check()` and need the verdict without string-matching). **GREEN BASELINE mode (`--baseline`, `baseline.ts`)**: `run.ts` resolves the stored record (`readBaselineSuites`) BEFORE calling `check()` and passes it as `baselineRecord` — `undefined` when `--baseline` was not requested (baseline mode OFF, behavior unchanged), `null` when it was requested but no record exists (every suite counts, and the run states the baseline is missing rather than passing in silence), or the (possibly empty) suite-path array from the record when one exists — those suites are dropped from the TEST step's parsed failures (`parseVitestFailures`) before the summary and exit code are decided, so only what THIS run newly broke is reported. `collectFailingSuites(root)` is the standalone counterpart `baseline.ts`'s `record` subcommand calls to produce a fresh record — same parser, independent of a full gate run. A recorded baseline NEVER reaches this parameter on a call that omitted `--baseline`: the commit / pre-push / plain forms of the gate always pass `undefined`, so a green baseline can never soften them. A `--baseline` run that suppresses a failure and exits 0 is not a proven-green tree, so it is never handed to `recordGreenInput` — the gate cache and the baseline never contaminate each other.
- `src/gate-cache.ts` (+ `src/gate-cache.test.ts`, and `src/check-cache.test.ts` for its wiring inside `check`) — the **GATE CACHE**: the SINGLE owner of `.dobby/gate-cache.json`, behind five verbs and nothing else (no caller ever touches those bytes — the shape, the atomicity, the LRU, the ignore guarantee and the stamps all live here). **`computeCodeHash(root)`** is the KEY: enumerate `git ls-files -c -o --exclude-standard -z` (tracked ∪ untracked-unignored — the set the tools actually read, and the set `git write-tree` would get wrong), drop the INERT paths (`docs/**`, `.claude/**`, and `**/*.md` except under a `__fixtures__`/`fixtures` segment, where markdown IS test input), content-hash the survivors with ONE `git hash-object --stdin-paths` (per-file spawns would cost more than the gate run this saves), then sha256 over the SORTED `path\0oid` pairs — the path is IN the pair, so a rename or a swap of two files' bytes moves the key even though the blob set did not, and a tracked file missing from the worktree drops out of the pair set so a deletion moves it too; `.gitignore`, `package.json` and the lockfile are deliberately NON-inert (they decide what the enumeration sees and what the gate RUNS). It answers null — "run everything, record nothing" — when the tree cannot be enumerated at all, AND for the two `--stdin-paths` LINE-FORMAT hazards: a path containing a NEWLINE (unexpressible, one path per line) and a path whose FIRST byte is a double quote (git C-UNQUOTES that line, so `"foo.ts"` is read as `foo.ts` — not a missing key but a WRONG one, frozen against every edit to that file) — AND for a tree holding an input that is **not a REGULAR FILE**: a checked-out SUBMODULE's gitlink, an embedded repository, a SYMLINK of any kind. git enumerates the gitlink (or the link) ITSELF and never what lies beneath or behind it, so a key built from the survivors alone would sit STILL while code the gate tools DO read changed — a hit served over a tree nothing ever gated. The test is ONE `lstat` predicate (`isFile()` is true for a regular file only), deliberately stricter than it must be: deciding per target kind would mean re-deriving soundness for dangling/looping/out-of-tree links and would open a window in which a link can be retargeted between two questions about it, while the price of the strict rule is one honest gate run. The INERT test runs FIRST, so a symlink or a nested repository parked under `docs/`/`.claude/` costs nothing. **`consultGreenInputs(root, hash)`** answers `{hit, at}`: was this exact input set already cleared by a FULL green gate under THIS dobby version and THIS `dobby.config.json`? Read-only by contract, and every degraded state (no file, malformed JSON, a stale stamp, a pre-upgrade flat-only record) is a plain MISS whose cost is one honest gate run. **`recordGreenInput(root, hash)`** remembers one: read-modify-write, move-to-front in an LRU of FIVE (branch switching and reverts return to trees already proven green; re-recording a known hash PROMOTES it, never duplicates), evicting from the tail. **`writeShipRecord(root, treeHash, exitCode)`** writes `ship`'s FLAT record while preserving the green inputs. **`ensureExcluded(root)`** keeps `.dobby/` out of the index — exported because `ship` must call it BEFORE its staging sweep, not when the record is finally written (and because an un-ignored cache file would enter the very code hash it records, a key that could never match again). It writes the rule to **`.git/info/exclude`, NEVER to `.gitignore`**: bookkeeping may not touch a VERSIONED file, and appending to (or creating) `.gitignore` made every green in-process `check` dirty the tree it had just judged — dirt inherited by `release` (which refuses a dirty tree outright), `preflight` and the pre-push backstop. The exclude file is repo-local, unversioned, addressed through `git rev-parse --git-path info/exclude` (so a linked WORKTREE resolves to the COMMON dir's copy — one rule covers every worktree), and feeds the SAME ignore machinery (`git check-ignore` honours it; the `--exclude-standard` enumeration above skips what it excludes), so the guarantee is identical while the cost to the working tree is nil — and, being outside the tree, the write cannot move the hash it is about to record. Both writers CARRY FORWARD whatever the other left behind, and a stamp mismatch drops BOTH records rather than re-stamping them (carrying a green input across an upgrade would resurrect a verdict this version never gave; carrying the flat record would hand the pre-push backstop a free pass). Writes are ATOMIC (temp file in the SAME directory + rename), so a `check` and a `ship` writing at the same moment in one worktree can never expose a half-written file to either reader; a write failure comes back as a NOTE, never a throw. Concurrent writers are **last-write-wins by design — there is no locking**: each renames its own COMPLETE file over the target, so the loser's record is simply forgotten, and since every write states only what its own run PROVED, a lost record costs one extra full gate run later and can never produce a false green (a lock would trade that for a lock file to leak, a stale lock to break, and a gate that can block on its own bookkeeping). `node:*` + the shared runner only (ADR-0008).
- `src/baseline.ts` (+ `src/baseline.test.ts`) — the **GREEN BASELINE** (`dobby baseline record [--json]`): names the test suites failing RIGHT NOW (via `check.ts`'s `collectFailingSuites`, a repo-relative path list) and stores them at `.dobby/baseline.json` — `record` always exits 0, whether the tree is spotless or on fire, because a record states a fact and never renders a verdict; a green tree still records an EMPTY set, a DIFFERENT thing from no record at all. `readBaselineSuites(root)` returns that list back, or `null` on ANY degraded read (no file, unreadable, unparseable, wrong shape) — the contract `check.ts`'s `--baseline` mode consults, reading `null` as "no baseline exists, everything counts". Deliberately a SEPARATE file from `gate-cache.ts`: the gate cache records only GREEN verdicts (codeHash → proven-green), so a repo carrying pre-existing red suites has nothing there to consult — the baseline answers a different question ("which suites were already red before this task started?") with its own reference run and its own file, never folded into the cache (which would overload one file with two unrelated questions). The dependency is ONE-DIRECTIONAL — `baseline.ts` imports `collectFailingSuites` from `check.ts`; `check.ts` never imports `baseline.ts` back, so `run.ts` resolves the stored record and hands it to `check()` as a plain parameter. `ensureExcluded` (`gate-cache.ts`) keeps `.dobby/` out of git's sight before every write, the same guarantee the gate cache relies on. `node:*` only (ADR-0008).
- `src/conventions.ts` (+ `src/conventions.test.ts`) — the **tier-(b) house-convention checks**: the layout rules no linter can see, because they are facts about the FILESYSTEM (a file's name, its directory, the sibling it must be paired with) or about TWO files at once. `scanConventions(root, files?)` returns `{ findings: [{ rule, path, message }], notes }` — PURE fs/content scanning, no AST dependency (ADR-0008), no spawn. Thirteen rules, each carrying its inventory id: **B1** no barrels (`src/**/index.ts(x)`, `src/routes/**` exempt), **B2** generic role-less basenames (`service|db|lib|api|actions|handlers|hooks|utils|models|tables|entities` — matched on the WHOLE basename, so the blessed `db.server.ts` is spared), **B3** `.client.ts` (a false boundary suffix — use `.browser.ts`), **B4** type-based bucket directories (`src/{components,services,hooks,lib,utils}` + any `-components/`; `src/shared/` is blessed), **B5** `pgTable(` outside a co-located `schema.ts`/`schema.gen.ts` or inside a central `src/schema/`·`src/db/schema/`, **B6** a `collection.browser.ts` with no sibling `functions.ts`, **B7** the CLOSED env exception set (`process.env`/`import.meta.env` under `src/**` + the root configs, allowed only in the env module and the out-of-Vite files — the tier-(a) `noProcessEnv` allowlist VERBATIM, so the two tiers can never disagree; comments are stripped before the match, so prose that NAMES the API is not a read), **B8** server-only symbols in the built client bundle (`.output/public` AS IT STANDS ON DISK — the gate plans the step after `build` so the common path scans a fresh bundle; ABSENT build output = a skip NOTE, never a silent pass), **B9** a module directory (≥1 role file) with no `CONTEXT.md`, **B10** react-email templates outside `src/emails/`, plus the three rules DEMOTED from tier (c) because GritQL plugins are single-file: **C2** `createMiddleware` in a `.server` file, **C3** a `createServerFn` chain with no `.middleware(…)` call at all (a same-file statement scan — see Invariants for its ceiling), **C12** the `.pick({…})` ↔ `.select({…})` projection pair across `collection.browser.ts` and `functions.ts` (balanced-brace text parse; a `db.select(<identifier>)` resolves to its same-file hoisted `const <identifier> = {…}` literal; UNPARSEABLE = a skip note, never a finding). Two modes: project-wide (every rule, `src/**` + the root config layer + the bundle) and per-file (`files` = ABSOLUTE paths — only the rules that judge those files; the whole-tree rules B4/B8/B9 and ALL notes are out, so the edit hook never nags about a neighbour's omission or the directory's pre-existing debt). VENDORED trees (`src/shadcn/**` + the legacy `src/components/ui/**`) are excluded from the scope in BOTH modes — the tier-(a) preset's excludes mirrored (`biome/core.jsonc`), because vendored code answers to upstream shadcn, not the house style (`src/shadcn/utils.ts` is shadcn's own `components.json` contract and cannot rename to satisfy B2), so a vendored file needs no `dobby-allow`. The escape hatch: `// dobby-allow <RULE-ID>: <non-empty reason>` — anywhere in the judged file for a per-file rule, in the comment run directly above the chain for C3 (per chain), in the directory's `CONTEXT.md` for B4; honored allows are counted in a whole-tree note. `check.ts` executes it; `tasks.conventionsEnabled` gates it.
- `src/lifecycle.ts` — the action-command executors (the inferred `db:*` tasks, `update`, `dev`, `build`, `up`/`down` — `up` now owns the folded setup phase). The IMPURE counterpart to the pure planners in `tasks.ts`: it resolves the workroot, touches the filesystem, and spawns children (always through `runner.ts`, cwd pinned to the workroot), returning DATA (`DbTaskReport`/`UpdateReport`/`DevReport`/`UpReport`/`DownReport`) that `run.ts` renders. `planDev(cwd)` is the `dev` CAPTURE path (used by `run()` for `--dry-run` and the no-app gate): detect capabilities, `devPlan`, and fold "no app main" into the hard "nothing to run" error — no spawn. `runDev(cwd)` is the `dev` STREAMING path (used ONLY by index.ts): the native `.vite` cache-clear (`rmSync`), then the portless-wrapped main (portless resolved BUNDLED via `runner.resolveBin`, run via `process.execPath`) + the consumer-local secondaries spawned as ONE managed group (`runManagedGroup`) — each child DETACHED via `runner.spawnDetached`, and ANY child exit or a SIGINT/SIGTERM to dobby tears the whole group down (`killGroup` → `process.kill(-pid)`), resolving with the MAIN's exit code — and, before spawning, `planDev` refuses a LIVE registered twin (`pidfile.liveRegisteredPid`, exit 1 naming the pid + `dobby down`), while `runDev` itself calls `pidfile.writePidfile` on startup (so `up`'s in-flight retry and a later `down` can find it) and `pidfile.clearOwnPidfile` on its own teardown. `planDev` RESOLVES every bin (consumer app/secondary bins + the bundled portless) via `runner.resolveBin` into a `ResolvedDevPlan`, so the `--dry-run` render and the real spawn read the SAME resolved paths (part c: the resolution is observable in the plan). A detected-but-not-installed vite degrades to a `dobby up` failure note (exit 127). The streaming spawn + kill mechanics are NOT CI-tested (they spawn real servers) — covered by the wrap-stage human smoke + the QA's live recipe. `buildSetupPlan(root, config)` builds the ordered SETUP-PHASE plan (a `SetupAction[]`) `up` runs first — (1) `bun install`, (2) the PRE-PUSH BACKSTOP install (planned + executed by `hook-install.ts`, which also owns its `PrePushHookAction` member of the `SetupAction` union; ordered after install so a fresh clone has the local bin the shim execs, and NEVER a phase failure — a foreign or unwritable hook leaves the workspace perfectly runnable and there is no honest `UpReason` for it), (3) `.worktreeinclude` re-materialization (LINKED-worktree only), (4) config `setup[]` extras — and `executeSetup(plan, root, childOutputToStderr)` runs it fail-fast (returning the first failing step's exit code + a `failure` note + the machine-readable `UpReason`; a re-materialization copy that throws is a REPORTED `worktree-copy-failed`, never an escaping exception). A LINKED worktree is detected by `git rev-parse --path-format=absolute --git-dir` ≠ `--git-common-dir`; the MAIN checkout root is the parent of the common `.git` dir, where `.worktreeinclude` is read; each pattern is matched against the main checkout (literal fast-path; simple `*`/`?` globs walk the tree skipping `.git`/`node_modules`), and any match MISSING at the worktree is copied over (idempotent — never overwriting a present file). `DOBBY_SKIP_INSTALL=1` is a documented TEST SEAM that skips only `bun install`. No db capability, or an unknown name, is a hard error whose message already lists the available (short) drizzle task names. - `src/hook-install.ts` (+ `src/hook.test.ts`) — the **PRE-PUSH BACKSTOP**: the `check --pre-push` mode, the hook SHIM, and its install. `prePushCheck(cwd, stdin)` reads git's pre-push stdin contract — one `<local-ref> <local-sha> <remote-ref> <remote-sha>` line per ref, of which ONLY FIELD 2 is ever parsed (field 1 is `(delete)` on a deletion and a raw object name on `git push <sha>:<ref>`), an all-zeros field 2 (40 or 64 of them — SHA-1 vs SHA-256) is a deletion and is skipped, and EMPTY stdin (or a delete-only push) is a legitimate exit-0 no-op that never runs the gate. Each pushed sha is peeled with `git rev-parse <sha>^{tree}` (which also peels an annotated tag); an unpeelable sha exits 128 and means NO KEY — the gate runs. **GATE CACHE** (`.dobby/gate-cache.json`, written by `ship`; the shape is restated here rather than imported, so the backstop never depends on the commit ceremony): the key is COMPOSITE (spec Decision 8) — EVERY pushed tree equal to `treeHash` AND `dobbyVersion` equal to the running version AND `configHash` equal to the sha256 of the current `dobby.config.json` BYTES AND `exitCode` 0 — because a tree hash alone would serve a stale pass across a dobby upgrade or a config edit, and a cached RED says nothing about a tree whose findings may since be fixed. A hit prints `gate cache hit (<tree>)` to stderr and exits 0 WITHOUT running the gate; otherwise `check([], root, {}, false)` runs IN-PROCESS — **fix=false is load-bearing** (a hook must never rewrite the bytes being pushed) — and a nonzero verdict exits with the gate's own code and prints the findings WHOLE (its own UNCAPPED renderer, never `run.ts`'s 50-per-tool `formatCheck`: the v0.5.1 incident was a summary read as the whole truth). The **SHIM** is a generated `/bin/sh` script (`#!/bin/sh`, then the marker line `# dobby-managed pre-push backstop — do not edit`) carrying only the ADR-0012 double guard (`[ -f dobby.config.json ] && [ -x node_modules/.bin/dobby ] || exit 0` — never a network-resolved dobby, which is an unrelated npm package) and `exec node_modules/.bin/dobby check --pre-push`: stdin flows through `exec`, the CLI's exit code becomes the hook's, and every decision stays in TypeScript where `run(argv, cwd, stdin)` can reach it. The **INSTALL** is a `SetupAction` of `up`'s setup phase (Decision 7: ALL consumers, idempotently — the setup phase runs even for a no-app project): the target is `git rev-parse --path-format=absolute --git-path hooks` + `/pre-push`, which resolves to the COMMON dir from any linked worktree (one install covers them all) and honors `core.hooksPath`; absent → write + chmod 755; a hook carrying the MARKER → overwritten (idempotent upgrade); a FOREIGN hook → never touched, and the refusal is named in the `up` plan (refuse-and-report; lefthook's fingerprint file and husky's repo-GLOBAL `core.hooksPath` were both rejected). Documented bypass: `git push --no-verify`. `node:*` + the shared runner only (ADR-0008).
- `src/ship.ts` (+ `src/ship.test.ts`) — the **COMMIT CEREMONY** (`dobby ship [--message-file <f>] [--pr-body-file <f>] [--json]`), a domain module behind the `command.ts` contract: validate `--message-file` BEFORE touching anything (a ceremony that cannot produce a message leaves the tree unstaged, un-formatted, un-gated) → `git add -A` when nothing is staged (a caller-staged subset is respected only until the gate has spoken) → the **GATE composed IN-PROCESS** (`check([], root, {}, true)` — never a `dobby` subprocess, so there is ONE gate implementation and ONE exit code) → ensure `.dobby/` is excluded and re-stage the WHOLE tree (the gate judges the working tree, so a committed SUBSET would record a green verdict for a tree that was never checked; the ignore rule lands in `.git/info/exclude`, so it adds nothing to the commit) → `git commit -F <message-file>` → push PINNED to origin (`-u origin HEAD` when there is no upstream; a non-origin upstream is overridden to origin with a `pushNote`, tracking config untouched) → `gh pr create --body-file`, gated on a NON-TRUNK branch (`main`/`master` have nowhere to open a PR from) and on the branch having none yet. **THE EXIT CODE DECIDES**: a nonzero gate ends the ceremony with the gate's OWN code, printing the findings WHOLE through ship's private uncapped renderer (a documented duplicate of `run.ts`'s `formatCheck`, which caps at 50 per tool — the v0.5.1 incident was a sample read as the whole truth), and commits NOTHING — so no cache entry can ever exist for a tree that did not pass. After a green gate it records the **flat gate-cache record** `hook-install.ts` reads (`.dobby/gate-cache.json`: `{at, configHash, dobbyVersion, exitCode, treeHash}`, the tree hash taken AFTER the stage) — ship OWNS the KEY (`git write-tree`, which is only equal to the committed `HEAD^{tree}` because it runs after the sweep) and DELEGATES the BYTES to `gate-cache.ts`'s `writeShipRecord`, the file's single owner, which preserves the GREEN INPUT SETS the same run's in-process gate recorded there moments earlier (a local writer would serialize the flat record alone and silently un-cache every later `dobby check`); `ensureExcluded` is imported from that same module rather than duplicated, and is called at step 3 because the rule must exist BEFORE the staging sweep, not when the record is finally written. Because the in-process gate is an ordinary `check()`, ship also CONSULTS that cache: a ceremony over a tree an earlier `check` already proved green skips the inferred steps and says so through `gateNote`. A detached HEAD is refused as step 0, before any mutation (the ceremony needs a named branch). ## Interface

`run(argv: string[], cwd: string, stdin?: string): Promise<{ exitCode: number; stdout: string; stderr: string }>`

- bare (no positional) → the capability-filtered usage on stdout, exit 0. The Commands list is COMPUTED from the cwd's detected capabilities (`usageCommands`): universal commands (env/instructions/check/update) always, dev/up/down only with `vite` (`up` is the prepare + probe entry point), db:* only with a db capability (the ACTUAL resolved short drizzle names). The field-report fix: the old static help advertised dev/up/down/db:* in repos with neither capability.
- `--version` / `-v` → package version + newline on stdout, exit 0.
- `env` → the environment snapshot on stdout, **always exit 0** (env NEVER fails; unresolvable facts are null). Fields:
  - `cmux` — the `CMUX_WORKSPACE_ID` value, or `null`.
  - `worktree` — the enclosing git worktree root (git's resolved path), or `null` outside a repo.
  - `branch` — the current git branch, or `null` outside a repo / on detached HEAD.
  - `capabilities` — the detected capabilities as a comma-separated list, or `none`.
  - `config` — `true`/`false`: whether a parseable `dobby.config.json` exists at the root.
  - `dbTasks` — the INFERRED `db:<task>` command names as a comma-separated list (`db:check, db:generate, db:migrate, db:push, db:studio` for a drizzle project), or `none`; a JSON array (`[]` without a db capability) under `--json`. Read from the same map `dobby db:<task>` resolves through, so the reported names always run.
  - `devUrl` — the portless-resolved dev URL for a vite project (`portless get <name>`, name = the package.json `portless` key or the `@scope/`-stripped package name), or `null` (no vite capability / portless missing / errors). Network-free — a local CLI resolve, never a liveness probe.
  - `runPane` / `browserPane` — the kit pane surface refs, discovered through cmux IPC when `CMUX_WORKSPACE_ID` is set (surfaces titled `dobby-run-<slug>` / `dobby-browser-<slug>`, slug = workroot basename), else `null`.
  - `env --json` → the same facts as one JSON object: string|null scalars, `capabilities` + `dbTasks` as JSON arrays, `config` as a JSON boolean.
- `instructions <topic> [--json]` → the INSTRUCTION CATALOGUE half of the environment adapter seam: for the detected environment, what the MODEL must do for `topic` (`start` · `stop` · `browser` · `rename`), since dobby cannot act there on its own behalf. Universal in the help (never capability-filtered — a no-app project still needs `rename`/`browser`). `start`/`stop`/`rename` fail hard outside a git repo, exactly like `up`/`down`; `browser` does NOT — it degrades to an empty workroot/slug/devUrl and still answers, since QA and a manual-setup gate may call it from outside a resolved worktree. `--json` → `{applies, environment, text, topic}`; the text form prints `text` + a newline when `applies`, else `not applicable in <environment>: <topic> has nothing for the model to do here` at exit 0 — the CALLER (this rendering), never the adapter, owns that not-applicable line. An unknown/missing topic subcommand is the ordinary subcommand-validation refusal, exit 1.
- `check [file...] [--fix] [--no-cache] [--lint|--types|--unused|--build|--test]` → the quality gate. No file args = the project-wide pipeline (`tasks.ts`): full gate (no flags) = biome, tsc, knip, build-if-vite, conventions-if-react/tanstack-start, test-if-vitest, + config `checks[]` extras; ANY selective flag = run ONLY the flagged tool steps (extras AND conventions excluded — conventions has no flag of its own). File args = biome over those files + the convention rules that judge them (selective flags ignored). `--fix` applies biome's SAFE fixes FIRST — project-wide `biome check --write .` (reaching the config files too), or over just the named files on the per-file path — then runs the selected pipeline and reports whatever remains; it composes with the selective flags (`--fix --lint` = fix then lint-report) and with the no-flag full gate, and NEVER applies biome's unsafe rewrites (`==`→`===`). **This is the pre-commit standard: run `dobby check --fix` before committing.** `dobby ship` is the ceremony that does it for you — it composes this gate IN-PROCESS (never a `dobby` subprocess) between the stage and the commit, so the `/dobby:commit` skill never runs the gate by hand; anyone committing outside `ship` (a human, a script) runs `--fix` first, and `check --pre-push` is the backstop that catches whoever didn't. The **conventions** group is dobby's own tier-(b) house-convention scan (`conventions.ts`, no spawn) — barrels, generic filenames, `.client.ts`, type-based bucket dirs, table/schema co-location, the collection↔server-fn pair, the closed env exception set, server-only symbols in the built bundle, module `CONTEXT.md`, email-template placement, plus the cross-file middleware/guard/projection rules — reported for a `react`/`tanstack-start` repo only, each finding as `path:0 <ruleId>: <message>`. Token-lean stdout: one `file:line message` line per finding, grouped + labelled per tool, capped at 50 per tool (`…N more` tail); then each step NOTE on its own line — a capability skip (`build: skipped (no vite capability)`) or a build/test/extra failure. A capability-gated step whose capability is absent is skipped with that single note (a skip is NOT a failure). When ANY tool ran on a dobby DEFAULT config (config-less defaults, ADR-0015 — the consumer ships no config of its own for biome/knip/vite/vitest, so dobby supplied its shipped preset via the tool's native flag) the run appends ONE token-lean note — `configs: biome=default(react) · knip=default · vitest=default` — omitted entirely when every tool used a consumer config. A step that exits nonzero but produced ZERO parsed findings (a crashed tool — startup/config error) surfaces, under its `<tool>: failed (exit N)` note line, a clearly-labeled tail of the tool's raw stderr (stdout when stderr is blank), capped to the last ~40 lines / ~4KB — so a findingless CI crash (the field bug) is diagnosable; findings-producing failures are unchanged. The vitest TEST step instead parses its `--reporter=json` output into a real `test: N suite(s) failed` summary (one capped line per failed file — message + first in-repo frame; raw tail only when that JSON is unparseable), TRANSLATING vitest's `Error: STACK_TRACE_ERROR` placeholder — what a test killed by its own timeout is reported as — into an explicit `test timed out (over the spawn budget …)` line naming machine contention as the usual cause, since echoed verbatim it reads as an unexplained crash, and — ONLY when it runs under dobby's react vitest default — it compares env files by KEY NAME (never value): a `.env.local` with no `.env.test` appends the inherits advisory (`test: vitest inherits .env.local (absent in CI) …`), an INCOMPLETE `.env.test` appends a missing-keys advisory (`test: .env.test is missing N key(s) …`), a complete superset is silent. ALL selected steps run (report everything, no stop-at-first-tool); exit = the FIRST failing step's code (findings ⇒ 1) or 0 when clean, and 1 on a hard error (outside a git repo / a bundled tool unresolvable — message on stderr). **The gate cache makes a re-run of an unchanged tree free**: a project-wide run keys the working tree's non-inert files (`gate-cache.ts`) and, when that exact input set already cleared a FULL green gate under this dobby + this `dobby.config.json`, prints `gate skipped: inputs unchanged since last green (<short-hash> @ <at>)` and skips the six inferred steps — the config `checks[]` extras still run and their verdict is the exit code. Editing prose (`**/*.md` outside a fixture dir), `docs/**` or `.claude/**` does NOT invalidate it (the inert set — nothing the gate reads); everything else does, `package.json`/`bun.lock`/`.gitignore` included. Selective flags are served by a full-green hit but never record one, the per-file path and `--hook` never touch it, and **`--no-cache`** ignores the hit and runs everything (still recording a green full gate).
- `check --hook` → the edit-time PostToolUse mode. Reads the hook payload from **stdin** (`{ tool_name, tool_input: { file_path }, ... }`), applies biome's SAFE auto-fixes to the edited file IN PLACE, adds the tier-(b) convention findings about that ONE file (stack consumers only — scoped per-file, so a neighbour's violation never surfaces), and surfaces ONLY unfixable findings: exit **2** with the token-lean findings on **STDERR** (the channel Claude Code shows the model on exit 2 — never stdout). Every guard is a **silent exit 0** (empty stdout AND stderr): unparsable payload / no `file_path` / missing file / not a git repo / no `dobby.config.json` marker at the workroot / file outside the workroot / extension outside `ts,tsx,js,jsx,json,jsonc,css` / biome could not run / biome fixed everything and the file breaks no convention. Harness noise must never block an edit. Invoked by `plugin/hooks/hooks.json` through a double-guarded LOCAL-bin shell one-liner (config marker + executable bin present, else exit 0; never `bunx`).
- `check --baseline` → judges the TEST step against the **green baseline** (`baseline.ts`) instead of the whole tree: a suite already named in `.dobby/baseline.json` (written by `baseline record`) is dropped from the failure summary, so only what THIS run newly broke is reported. No record at all still counts every failure AND states the record is missing rather than passing in silence. linear reads UPPERCASE `VON-123` + linear.app URLs and NEVER `#42`; local has no pattern), so anything unmatched is a `prompt` goal; `id` is bare (`"42"`, no sigil), `lifecycleLink` is `Closes #<n>` / `Fixes <KEY>` emitted HERE so commit/scope never re-derive it, `slug` is a few kebab words (an issue goal starts from `issue-<n>` / the key), `slugCollision` checks the branch `worktree-<slug>` AND `.claude/worktrees/<slug>/`, and `hardStop` is set ONLY for a github issue goal while gh is unreachable (an issue goal has no free-text fallback — D8's one hard stop; free text always continues). A missing operand (concept / issue id / goal reference / `--title` / an unreadable `--body-file`) is a refusal on stderr with exit 1 naming what is missing, and nothing is created.
- `release [--bump patch|minor|major] [--notes-file <f>] [--dry-run] [--json]` → cut ONE release, through the target adapter `dobby.config.json#release.type` selects. CONFIG-GATED: without a `release` key the command does not exist at all (absent from the help, unknown to the dispatcher). Phases, each recorded in `phases[]`: preflight (MAIN checkout only, on `main`, clean tree, `git pull --ff-only`, CI green **on the commit being released** (HEAD, or its parent on the resume run, where HEAD is the unpushed release commit), `adapter.preflight`) → version (inferred from the commits since the last `v*` tag) → bump (indentation-preserving manifest rewrite + lockstep, the gate over the bumped tree, a LOCAL `release: v<V>` commit) → changelog → publish (`adapter.packGate` → `adapter.publish` → tag → push → `gh release create` → `adapter.smoke`). Three stops, all exit **1** so none can read as a finished release: `{needsDecision: "first-release"|"0x-major", context:{currentVersion, commits[]}}` (nothing touched — answer with `--bump`), `nothing to release` (the last tag is already on HEAD), and `{needsNotes: true, version, changelog:{groupedBy, groups, since}}` (everything mechanical done, the bump commit LOCAL, nothing pushed — author the notes and re-run with `--notes-file`, from a path OUTSIDE the repo). A completed release exits 0 with `{changelog, phases[], published: true, tag, version}`; `--dry-run` exits 0 with the version + changelog it WOULD cut, having touched nothing. The `npm` target lives in `release-npm.ts`; it reads two `release` keys of its own — `dir` (the publishable package dir, which every npm/bun spawn is pinned to) and the optional `smoke`, an ARGV ARRAY (`["bun", "install", "-g", "…"]`, never a shell string) run after the registry serves the published version, whose nonzero exit fails the smoke phase. The `homebrew-cask` target lives in `release-cask.ts`; it reads `tap` (the tap REPOSITORY, e.g. `kvnwolf/homebrew-tap`), `cask` (the cask TOKEN, i.e. the `Casks/<cask>.rb` it writes) and the OPTIONAL `notaryProfile` (a notarytool KEYCHAIN PROFILE name — its presence adds the Developer ID + profile preflights and the submit/staple/spctl gates to packGate; its ABSENCE is the un-notarized flow, which spawns no Apple tool at all; a present-but-EMPTY value is a config mistake and is refused by name, never read as "no"), adds the two optional phases to the run (`bumpExtras` in the bump, `post-release` between the GitHub release and the smoke), and its smoke REPORTS the `brew install --cask` command instead of running it.
- `migrate preflight | migrate verify` (`--json`) → the two mechanized ends of `/dobby:migrate-config` (fails hard outside a git repo; both are READ-ONLY and touch nothing). `preflight` answers `{verdict: "already-migrated"|"migration-needed", signals:{legacyYaml, oldEraConfig:{path,hasRun,vpExtras}|null, viteplusDep, aliases[], viteHooks, vpTaskTable, prepareScript, conductor}, snapshot:{toolchainDeps[], preservedKeys[], worktreeinclude, scripts[], toolConfigs:{biome,vite,vitest,drizzle}, envTest, ci[], vercelJson, tracker:{source,type,team}}}` — `already-migrated` iff NO legacy signal fired AND `dobby.config.json` is new-schema AND `tsconfig.json` extends `@kvnwolf/dobby`. `verify` runs the gate IN-PROCESS and answers `{ok, check:{exitCode, failingSteps[]}, env:{capabilities[], config, devUrl, dbTasks[]}, residual:{legacyFilesRemaining[], deltaConfigsKept[], trackerIncomplete}}` — `failingSteps[]` is never empty for a nonzero `exitCode` — `ok` = a green gate AND no legacy artifact left AND a fully-pinned tracker (a KEPT delta config is reported, never held against the repo). Every path in both payloads is REPO-RELATIVE. Both exit **0 with the payload for EVERY verdict** (they inform, they never refuse); exit 1 is reserved for the two unanswerable cases — outside a git repository, and a gate that could not START.
- `spec lint [<file>]` · `map lint|next|claim <slug> [<file>]` · `skill lint <dir>` · `wizard verify <script>` · `arch-report verify <file>` · `handoff finalize <file> [--focus <s>]` · `brief lint (--file <f>|--issue N)` (all `--json`) → the ARTIFACT LINTERS. One report contract: findings one per line as `<where>: <message>`, exit 1 on ANY finding, `ok` + exit 0 when clean, `--json` → `{ok, findings: [{check, message, where}], notes}` as the sole stdout line; an unresolvable TARGET (a file that is not there, a slug the map never had, a gh call that failed) is a hard error on stderr (never a clean verdict). A check that could not RUN — shellcheck absent, a repo with no `.github/workflows` — is a NOTE, never a finding and never an exit code. `spec lint` defaults to `<workroot>/STATE.md`'s `## Spec`, `map` to the newest `docs/maps/*.md`. `map next` answers `{path, question, slug, title, type}` (nulls when nothing is claimable) and writes nothing; `map claim <slug>` rewrites that ticket's `Status:` line to `in-progress` in place and answers `{claimed, ok, path, status}`. `handoff finalize` prints the document's ABSOLUTE PATH as its clean verdict (and carries it as the `path` payload key) — its output IS the skill's "echo the path" step; `brief lint --issue N` reads the newest comment on the issue through `gh`.
- unknown command / malformed flag → error + the SAME capability-filtered usage on stderr, exit 1 (a no-capability repo's unknown-command usage hides dev/up/down/db:*; a drizzle-only repo's shows the short db names). Unknown commands additionally carry the version-skew hint line `if this command is expected, run \`bun update @kvnwolf/dobby\`` as the second line.

The bin is the only reader of `process.cwd()`; every other caller (tests, future subcommands) passes `cwd` explicitly.

## Invariants

- **Runtime-portable core**: `run.ts`, `detect.ts`, `config.ts`, `envinfo.ts`, `environment.ts`, `adapters/*.ts`, `pidfile.ts`, `runner.ts` use `node:*` imports (plus the plain JSON import) only — no `Bun.*` globals, no `bun:` modules — because vitest imports them at Node/Vite runtime while Bun runs them in production. `runner.ts` uses `node:child_process` `spawnSync` (never `execFileSync`, so a nonzero child exit is data not a throw; never `Bun.spawn`).
- **Signals check `dependencies ∪ devDependencies` only** — NEVER `peerDependencies`; missing dependency fields are treated as empty objects.
- **Signal matching forms**: exact dependency name (`react` never matches `react-email`), OR-of-several (`drizzle` ← `drizzle-orm`|`drizzle-kit`), and scope prefix (`react-email` ← `@react-email/*`). Fixed catalog order: `vite`, `tanstack-start`, `react`, `neon`, `drizzle`, `react-email`, `vitest`, `expo`.
- **`env` never fails**: `collectEnv` degrades every unresolvable fact to `null`/`false`/`[]`, and formatting cannot throw — the exit code is always 0. (Action commands added in later tasks fail hard; `env` is the snapshot exception.)
- **`config.ts` is the ONLY reader of `dobby.config.json`** — tolerant tri-state (missing → null / unparseable → error object / valid → config); no other module opens that file.
- **The detectors are pure over their `root` argument** — they never read `process.cwd()`; `run()` owns all output formatting (the modules return data, never rendered lines).
- **Workroot pinning is THE runner invariant**: every child process spawns through `runner.ts` with `cwd` pinned to the resolved workroot (`git rev-parse --show-toplevel`), NEVER the ambient cwd — killing the run-in-the-wrong-checkout bug class. `resolveWorkroot` is the sole exception (it runs git FROM the ambient cwd, because that is how the workroot is discovered). Action commands outside a repo fail hard (`requireWorkroot`); `env` is exempt and degrades to null. `up`'s setup phase consumes the fail-hard + `runInherit` foundation (`bun install` + config `setup[]` extras).
- **One bin resolver, owning-tree-first, PATH last (`runner.resolveBin`).** Every dobby TOOL spawn routes through it; system tools (git, curl, cmux, sh, bunx, gh, npm, bun — neonctl via bunx) stay bare and never do. BUNDLED tools (portless, biome, tsc, knip, taze) ALWAYS prefer dobby's OWN dependency tree (the whole point of bundling is zero reliance on globals) — resolved PATH-INDEPENDENTLY by walking `node_modules/.bin` up from the runner module's own location, never a `which`-style PATH lookup. CONSUMER tools (vite, vitest, drizzle-kit, email) ALWAYS prefer the consumer's own `node_modules/.bin` (never a global that may version-skew). PATH is a last-resort fallback in BOTH scopes, never the first choice — this is the field-bug fix (a bare `portless` off PATH made `env` print `devUrl: null`). The `--dry-run` plans for dev/db RENDER the RESOLVED absolute paths so the resolution is observable, and the real spawn reads the SAME resolution. `check.ts` keeps its own equivalent bundled/consumer resolution (`binFrom`/`pkgRootFrom`/`resolveConsumerBin`, run via `process.execPath`) — an already-correct site with a real-tool integration test, deliberately not rerouted to avoid regressing it.
- **`up`'s setup-phase re-materialization is gated on being a LINKED worktree, not on `.worktreeinclude` presence** — a plain checkout carrying the file copies NOTHING (the gate is `--git-dir` ≠ `--git-common-dir`), and the copy fills MISSING files only, so a second `up` (or a locally-edited worktree file) is never clobbered.
- **The pre-push backstop owns EXACTLY one file, and only if it wrote it.** The marker line (`# dobby-managed pre-push backstop`) is the identity test: a pre-push hook without it is somebody else's and is reported, never chained into, wrapped, or replaced — and `core.hooksPath` is never set (it is repo-GLOBAL and would disable every other hook the repo has). Three more rules that must not soften: the gate runs with **fix=false** (a push must not rewrite the tree it is pushing), the block prints the findings **WHOLE** (the v0.5.1 incident was a summary read as the whole truth), and the shim stays a **dumb guarded exec** — every decision lives in `hook-install.ts`, reachable through `run(argv, cwd, stdin)`, because a shell script is only reachable through a real `git push`. Corollary: `index.ts`'s stdin drain MUST list `--pre-push`; without it the hook feeds the CLI nothing and every push passes silently.
- **`env` stays network-free**: devUrl and pane refs are resolved through LOCAL CLI/IPC only (`portless get`, `cmux list-*`) — no liveness probe, no HTTP. Any tool being missing/erroring folds the fact to null, and `env` still exits 0.
- **Capabilities read the caller's cwd, not the workroot** — a single-package project runs dobby at its root, and the task-1 fixtures (which live inside this repo) rely on capability detection reading their own `package.json` rather than this repo's top-level.
- **The usage/help is capability-filtered over the PASSED cwd, never a workroot resolve** — `buildUsage` calls `detectCapabilities(cwd)` (the same detection `env` uses), so the fixtures that live inside this git repo report their OWN capabilities; a workroot resolve would collapse every fixture to this repo's (empty) set. Universal commands (env/instructions/check/update) are never filtered out; dev/up/down gate on `vite`; db:* gates on a db capability and shows the resolved names from `dbTasks`. The Options block stays static (a flags reference).
- **`check` shells out — never an in-process tool API**: biome + tsc run as child processes with machine reporters (`biome --reporter=json`; parse `tsc --pretty false` text — TS7 has NO JS API), never the Biome WASM js-api. The tool binaries resolve from DOBBY's OWN dependency tree (`createRequire(import.meta.url)` → the package's `bin` field), NEVER the consumer's — consumers install nothing. The CONSUMER's `biome.jsonc` / `tsconfig.json` are the live configs (thin-file model: they extend `@kvnwolf/dobby/tsconfig` and `/biome/*`), discovered by each tool walking up from the pinned workroot.
- **Biome findings count only `error`/`warning`** — `info`/`hint` diagnostics (e.g. the `recommended`-field deprecation notice) are surfaced by biome but MUST NOT fail the gate; the finding filter drops them so a clean project exits 0.
- **The check PLAN is pure (`tasks.ts`), the EXECUTION impure (`check.ts`)** — `checkPipeline` never spawns; all child processes stay in `check.ts` through `runner.ts`. build/test bins resolve from the CONSUMER's tree (never dobby's — dual-vite would break the consumer's plugins); biome/tsc/knip from DOBBY's. The vitest step's RUNTIME is node-if-present (a bare `node --version` probe, `process.execPath` fallback) — ONLY the vitest spawn, so a `bunx dobby check` doesn't run the consumer's tests under bun (whose module runner mis-resolves some deps); the fallback path notes the runtime it used. A capability-absent build/test step is SKIPPED with a single note, not a failure. Every SELECTED step runs regardless of earlier failures (report everything); config `checks[]` extras are the one exception — fail-fast among themselves. The exit code is the FIRST failing step's; selective flags subset the pipeline and exclude the extras.
- **The gate cache records GREEN and only green, and never touches the index — nor any VERSIONED file.** Only a FULL gate that ACTUALLY RAN and exited 0 may vouch for an input set: a SELECTIVE run (`--lint`, `--types`, …) is SERVED by a full-green entry (a full green proves any subset) but never RECORDS one, a HIT never re-records (its `at` must keep naming the run that actually proved the tree), and `--no-cache` skips the CONSULT while still recording its green (turbo `--force` — it skipped the consult, not the work); the per-file fast path and `checkHook` never touch the cache at all. Hashing is INDEX-NEUTRAL by construction — `git ls-files` + `git hash-object --stdin-paths`, both read-only, never `git write-tree` (which would stage what the developer is about to commit, AND miss the untracked-but-unignored files the tools do see). The bookkeeping is TREE-NEUTRAL by the same discipline: the ignore rule that keeps `.dobby/` invisible goes to `.git/info/exclude` (unversioned, common-dir, resolved via `git rev-parse --git-path`), never to `.gitignore` — a green `check` that appended there dirtied the very tree it had just judged, and `release`'s clean-tree precondition failed on dobby's own droppings. The file shape is ADDITIVE: `ship`'s flat five fields (`at`/`configHash`/`dobbyVersion`/`exitCode`/`treeHash`) stay byte-compatible with the INDEPENDENT reader `hook-install.ts` gives the pre-push backstop, and `greenInputs` (the LRU of five) rides alongside — each writer must preserve the other's record or the two silently un-cache each other. `gate-cache.ts` is the SINGLE owner of `.dobby/gate-cache.json`: `check.ts` and `ship.ts` call its verbs and never hash, read or serialize those bytes themselves. What the key does NOT cover is the documented v1 price — gitignored env files (`.env.local`) are invisible to it — and is also why config `checks[]` extras STILL run on a hit: arbitrary consumer shell may read anything. Where the key cannot be SOUND it is not computed at all: a tree holding an input that is not a REGULAR FILE (a checked-out submodule, an embedded repository, any symlink) has NO KEY — cache off, full run, nothing recorded, nothing said — because git hands over the gitlink or the link and never what lies beneath it.
- **ONE spawn budget, stated per FILE — never a per-test literal.** Suites here build scratch repos and drive REAL tools (git, biome, tsc, the CLI itself), 24 files in parallel, and the wall clock moves with the ambient environment: the same suite takes ~175s under a bare `vitest run` and ~780s under `bunx dobby check` (whose bunx env every spawn inherits). Vitest's defaults (5s/10s) kill honest work there and report `STACK_TRACE_ERROR`, which reads like a product bug. So `vitest.base.mjs` ships `testTimeout`/`hookTimeout` at **120s** — a CEILING, not a target — and every spawn-heavy suite ALSO calls `useSpawnBudget()` (test-helpers) at module scope, because a config-LESS invocation never reads the preset: `bunx vitest run src/release.test.ts`, the natural way to debug one suite, would otherwise get the 5s default. Per-test `}, 30_000)` arguments are GONE — each silently undercut the ceiling and was exactly what expired under the gate. Only a budget ABOVE the ceiling stays written out (the two 180s cask builds).
- **Convention rules SHRINK rather than approximate (tier b, `conventions.ts`).** At gate severity a false positive turns the gate red on CONFORMANT code, so: every content rule greps the CONSTRUCT (`pgTable(`, never the bare word), an unparseable projection is a skip NOTE and never a finding (C12), a missing build output is a skip NOTE and never a pass (B8), and C3 fires only on a `createServerFn` chain with NO `.middleware(…)` call at all — it matches the CALL, never its argument, so a hoisted `.middleware(sessionMiddlewares)` counts as guarded — it deliberately does NOT require the literal name `requireAuth` (a house app whose session middleware is named otherwise would go red) and it cannot know that a login/signup endpoint is legitimately public — a deliberately public endpoint is blessed per chain with `// dobby-allow C3: <why>` in the comment run above the declaration. B7's exception set is the tier-(a) `noProcessEnv` allowlist VERBATIM (`biome/react.jsonc`: the env module + the out-of-Vite files) — the two tiers must be edited together or the gate contradicts itself. The per-file mode drops the whole-tree rules (B4/B8/B9) and all notes: the edit hook judges what the model just wrote, never a neighbour's omission or its directory's pre-existing debt.
- **Tier (b) is CAPABILITY-GATED, never configurable.** The rules encode ONE stack (TanStack Start + Drizzle/Neon + Better Auth), so they ride the same `react`/`tanstack-start` fork as the tier-(a) biome preset and the tier-(c) GritQL plugins (`tasks.conventionsEnabled` is the single predicate). A non-stack consumer never sees the step at all — not even as a skip note.
- **Streaming split: `run()` is the CAPTURE seam, the bin owns the live stream.** A long-running `dobby dev` (a concurrent group with signal forwarding) cannot flow through the synchronous `run()` seam, so index.ts intercepts a CLEAN live `dobby dev` and hands it to `runDev`; `run()` handles only the `dev` `--dry-run` plan and the no-app gate — it NEVER spawns a dev server. `--dry-run` on a streaming command therefore always routes through the capture path (testable). **The split is FLAG-CLEAN by construction**: it fires only when the argv carries NO flag at all (`tasks.isLiveDev`, pure + unit-tested), because the interception happens BEFORE `run()`'s strict `parseArgs` and anything it swallows is never flag-validated — so ANY flagged dev (`--dry-run`, `--json`, an unknown `--no-share`) defers to `run()`, keeping ONE validator for the whole CLI (`dobby dev --no-share` and `dobby up --no-share` fail identically: exit 1 + usage). The dev COMPOSITION is pure (`tasks.ts` `devPlan`) and fully covered by dry-run plan assertions; only the spawn/kill EXECUTION (`lifecycle.runDev` / `runManagedGroup`) is impure and out of CI reach. `portless` wraps ONLY the main process (never the secondaries); the `.vite` cache-clear is part of the inferred vite dev; the managed group is DETACHED-spawned via `runner.spawnDetached` (cwd pinned) and torn down as a unit with `process.kill(-pid)` (`node:child_process`, no `concurrently` dep).
- **Config-less defaults are OVERRIDE-BY-PRESENCE, never merged (ADR-0015).** For every tool ONLY dobby invokes — biome, knip, vitest, vite, drizzle-kit — a consumer config FILE at the workroot is a TOTAL override: dobby spawns the tool BARE and its native discovery finds the consumer file. **The `ownFiles` presence lists MIRROR each tool's REAL native discovery** (a legal-but-unlisted form must NOT be silently overridden), each verified against the installed tool: biome `biome.json`/`biome.jsonc`; knip = its `KNIP_CONFIG_LOCATIONS` verbatim (`knip.json`, `knip.jsonc`, `.knip.json`, `.knip.jsonc`, `knip.ts`, `knip.js`, `knip.config.ts`, `knip.config.js` — knip 6.26.0 `dist/constants.js`) OR `package.json#knip`; vitest = the DEDICATED `vitest.config.{ts,mts,cts,js,mjs,cjs}` ONLY; vite = its `DEFAULT_CONFIG_FILES` (`vite.config.{js,mjs,ts,cjs,mts,cts}` — vite 8.1.5 `dist/node/chunks/node.js`); drizzle = only the forms drizzle-kit's bare discovery tries (`drizzle.config.{ts,js,json}` — verified against drizzle-kit 0.31.10 `bin.cjs`; NOT `.mjs`/`.mts`, which it never discovers, so listing them would be a false override). **Vitest DELIBERATELY excludes `vite.config.*`**: vitest natively falls back to a `test` block inside a `vite.config.*` when no dedicated `vitest.config.*` exists, but dobby counts ONLY a dedicated `vitest.config.*` as the override — house convention keeps test wiring in `vitest.config.*`, so a `vite.config.*` kept for app-plugin deltas must not silently disable dobby's vitest default (the one place dobby narrows a tool's native discovery, intentionally). ABSENT → dobby appends the tool's native config flag (biome `--config-path=` + `--vcs-root=`; knip/vite/vitest `--config`; drizzle-kit `--config=`) pointing at the SHIPPED preset resolved via `runner.resolveAsset` from DOBBY's own tree. **Which asset a capability selects is REQUIRE-ALL-IMPORTS for multi-import presets**: a capability alone NEVER picks a preset whose unconditional imports the consumer can't satisfy — `viteConfigSpec` picks `vite.tanstack.mjs` only when the dependency set (the same `deps ∪ devDeps` read detection uses, threaded from `scanCapabilities`) declares ALL FIVE packages it imports (`@tanstack/react-start`, `@tanstack/devtools-vite`, `@tailwindcss/vite`, `nitro`, `@vitejs/plugin-react` — all OPTIONAL peers), and `vitestConfigSpec` picks `vitest.react.mjs` only when `@vitejs/plugin-react` + `vite` are BOTH declared. **The MISSING-import outcome DIFFERS by tool, turning on whether the base fallback is FUNCTIONALLY CORRECT: vite is ALL-OR-ERROR, vitest DEGRADES.** A config-less `tanstack-start` app missing ANY of the five is a HARD ERROR — `viteConfigSpec` returns a discriminated `blocked` variant (`{ kind: "blocked"; missing }`) and the impure callers (check build step, `planDev`/`runDev`, `runBuild`) surface it through their EXISTING failure channels (check: a build-step failure note; dev/build: the plan/run error path — the 'nothing to run/build' twin; a blocked dry-run is an error, not a render), exit 1, naming the missing packages + BOTH remedies (install them, or ship your own `vite.config.*`, which overrides) — NEVER a silent `vite.base.mjs`, because base carries NO framework plugins so the app can't actually serve. `vite.base.mjs` is the default ONLY for a plain vite app (no `tanstack-start`). vitest instead DEGRADES to `vitest.base.mjs` when a react-variant import is missing — SAFE because vitest.base is functionally correct (tests still run, nothing silently broken). Single-import presets need no guard (biome/react extends a BUNDLED dobby dep; drizzle.base imports only the gating `drizzle-kit`). The DECISION (which asset per capability + dep-set, the flag form, the own-config filenames, AND the `default`-vs-`blocked` variant) is PURE (`tasks.ts` `*ConfigSpec`); the fs presence check + path resolution + turning `blocked` into args-or-error are IMPURE (`runner.configArgs`, and `runner.resolveViteConfig` which honors a present consumer config as an override that supersedes the block). The ONE config that ALWAYS stays is the consumer's `tsconfig.json` (tsc is NOT config-less-defaulted — other tools read tsconfig directly, and it carries per-project `paths`). Observability is non-negotiable: `check` emits the `configs:` note, and the dev/build/db `--dry-run` plans render the full `--config <abs>` path — override-by-presence is visible, never silent. The repo DOGFOODS this — its deleted root `vitest.config.ts` forces its own gate through the default.
- **`db:*` inference: drizzle-only → short names always.** drizzle is the ONE db tool (`dbTasks`, pure): its capability exposes the SHORT `db:*` names (`db:generate/migrate/push/check/studio`), each mapping to drizzle-kit; no drizzle → mode "none" and every `db:*` name is a hard error. The drizzle-kit bin resolves CONSUMER-local (never dobby's bundled tree). `update`'s taze resolves from DOBBY's OWN tree (bundled).

- **No credential-shaped literal is ever written out in SOURCE — the secret-scan fixtures are assembled at RUNTIME.** GitHub's push protection scans the source of every pushed commit, so a full-shape fake (`ghp_` + 36, `xoxb-<digits>-<digits>-<alnum>`, `AKIA` + 16, a credentialed `postgres://` DSN, a `BEGIN … PRIVATE KEY` header) written as one string in `artifact-lint-b.test.ts` BLOCKS the push that ships the test. Each fake is joined from inert fragments (`["xoxb", …].join("-")`) — never `+`, which the formatter folds back into a single literal — and the joined value still matches its `SECRET_PATTERNS` regex byte for byte. Same rule for prose: docs describe the shapes without spelling a complete one.
- **Kit material the CLI judges is VENDORED, never read from the plugin dir.** The wizard template (`wizard/template.sh`), the skill-frontmatter whitelist and the `/dobby:<skill>` list are copies inside this package, because `dobby` ships to CONSUMERS where `plugin/` does not exist — reading it would make every one of those checks a no-op in the field. The cost is drift: each copy names its canonical source in a comment and must be re-synced when that source changes (the wizard template byte-for-byte from `set -euo pipefail` down — a stale copy makes `wizard verify` reject honest scripts).

- **`up`/`down` safety invariants (load-bearing, must not soften).** Neon isolation is guaranteed: a neon-capability project with EITHER `NEON_API_KEY` / `NEON_PROJECT_ID` missing from `.env.local` makes `up` FAIL HARD — there is NO silent fallback to the shared main database. **The kit surfaces are now the MODEL's to open, in the order `up` hands the instructions over** — `rename` before `start` when both apply — but the SEQUENCING GUARANTEE `up` still owns is the one that matters: the `start` instruction is offered only once the setup phase and (when applicable) the neon branch have succeeded, and the liveness wait NEVER hands back a `start` instruction while a registered twin (`pidfile.liveRegisteredPid`) is already in flight — that would risk a second server on the same portless route. slug = workroot basename; the neon branch is `dobby/<slug>` (SLASH), the panes the model opens are named `dobby-{browser,run}-<slug>` (DASHES) in the instruction text, and the cmux WORKSPACE title is the PLAIN `<slug>` (no `dobby-` prefix — the prefix distinguishes the kit panes; the workspace title IS the goal identity). The `rename` instruction is offered WHENEVER cmux is present, after the setup phase and BEFORE the no-app gate — INDEPENDENT of the app gate, so a no-app project's report still carries it; `down` never touches the workspace title. Both commands are ACTION commands — fail hard outside a git repo (the git precondition wins over EVERY gate — `up`'s setup phase, its no-app gate, and its run phase). `up`'s setup phase runs BEFORE the no-app gate and the run phase, and a setup-phase failure short-circuits both (the run phase never starts). `down` NEVER signals a pid unless it passes BOTH ownership checks — the `ps` command-line `dobby dev` signature AND a start-time match (`ps` etime-derived process start ≤ pidfile mtime + 15s tolerance) — because the signature alone matches ANOTHER worktree's dobby dev (parallel goals are normal), so a recycled pid could still SIGTERM an unrelated workspace's process (pid-reuse guard: `isAlive`'s signal-0 EPERM counts any live pid alive, even another user's, so ownership is verified before the SIGTERM — a mismatch / unstat-able pidfile / unparseable etime / stale pid removes the file silently and signals nothing). The `--dry-run` plan and the real execution both derive from ONE resolved decision set so a dry run never lies about what a real run would do.
- **The environment-adapter import direction is one-way, never a cycle.** `environment.ts` (and every file under `adapters/`) must NEVER import `lifecycle.ts` — `lifecycle.ts` imports `environment.ts`, not the other way around, because `lifecycle.ts` is where the run-phase decisions (devUrl, neon, the liveness probe) live and `environment.ts` must stay usable from `dobby instructions` without pulling any of that in. `pidfile.ts` sits BELOW both (it imports neither), so both may import it freely without ever risking a cycle.

- **`release` safety invariants (each one is a field scar; softening any re-opens it).** (1) **PUBLISH-GATED PUSH** — the tag is created and pushed only AFTER `adapter.publish` succeeded, and a failed publish rolls the local bump commit back (`git reset --hard HEAD~1`) while it is still the UNPUSHED HEAD; a pushed tag for a version that never shipped burns that number for good. (2) **The manifest indentation is MEASURED, never assumed** — each file's own first indented line decides, and only the version VALUE is rewritten (v0.5.1 shipped a hardcoded `"\t"` that reformatted every 2-space manifest and turned CI red on the release commit itself). (3) **MAIN CHECKOUT ONLY** — a release cut from a linked worktree would tag and push the goal's branch. (4) **CI green is asserted IN CODE, on the commit being released** — `headSha` must equal that commit; a green run for some other one says nothing about the tree being published. It is HEAD, EXCEPT on the resume run, where HEAD is the local unpushed `release: v<V>` commit CI cannot have seen and the assertion moves to its parent (asserting against HEAD there would make the resume unreachable, and its only advice — "push and let CI finish" — would break invariant 1). (5) **Both human judgements stay with the model** — the version question (`needsDecision`) and the release notes (`needsNotes`) each STOP the command with data instead of guessing, and both stops exit 1 so no caller can mistake one for a finished release. (6) **`git describe`'s exit 128 is a FIRST RELEASE, not an error** — it fires both for a repo with no tags and for one with no `v*` tags, and its `fatal:` stderr is never forwarded.
- **Worker model/effort has ONE owner: each agent's own frontmatter, never a CLI-side recipe.** `plugin/agents/*.md` (`researcher`, `test-author`, `implementor`, `reviewer`, `qa`) declares its own `model`/`effort` directly, and `dobby.config.json`'s `frontmatter-model-effort` `checks[]` extra only checks that both keys are PRESENT — it never compares values against anything, because there is nothing outside those five files to compare against. `dobby env` carries no worker-consumption field at all. `/dobby:execute` dispatches the five worker agents directly (the Agent tool, named `subagent_type`) by following the dispatch protocol at `plugin/skills/execute/references/build-protocol.md` — prose the Architect reads and carries out itself, never a script or a separate execution engine. Normal execute is test-author (conditional) → implementor (+ its own Exit gate) → qa; the reviewer policy remains for explicit dispatch and missing-work-log safety review, not the normal task loop. There are no profiles, user selections, configuration/override surfaces, process executors, `claude -p`, host abstractions, or private-transcript scrapers.

## What's intentionally NOT here

- **No public share / tunnel (REMOVED).** dobby once wrapped the dev main in `portless run --ngrok …` by default (a `--no-share` opt-out, a `shareUrl` env field read from portless's `routes.json`, an `ngrok version` degrade probe). It is GONE — the whole flag/probe/field/note surface, not merely defaulted off: an ngrok binary present-but-unauthenticated made portless fail HARD (a broken bring-up, not a degrade), and the URL was a NEW random one every session (no stable domain — portless 0.15.3 offers no domain pass-through), so nothing durable could be built on it. `dobby dev`/`dobby up` run the app LOCAL-ONLY on the stable portless `devUrl`; `--no-share` now hits the ordinary parse-error path (exit 1 + usage). Re-adding it means a tunnel with a persistent domain, not this.
- **The vite / vitest-react / drizzle presets import CONSUMER-resolved packages, never dobby deps** — `vite.base.mjs` imports `vite`, `vitest.react.mjs` imports `vite` + `@vitejs/plugin-react`, `drizzle.base.mjs` imports `drizzle-kit`; NONE is a dobby dependency (the dual-Vite invariant). This is exactly WHY the base/react split exists: `vitest.base.mjs` (and the `tsconfig`/`biome-core` bases) stay importable in a repo WITHOUT vite installed — such as dobby's own — while the vite-touching variants live in separate files a vite-free repo never loads. The preset assets are asserted by FILE READ (never imported at test time, since their imports don't resolve here); knip's `unlisted` report for the consumer packages is suppressed via the root `knip.ignoreDependencies`, the same lever the bundled tools use.
- **Deep cwd-pinning, exercised end-to-end only for extras** — `up`'s setup phase consumes `requireWorkroot` (fail-hard outside a repo) and `runInherit` (config `setup[]` extras + `bun install`), and its tests observe extras landing at the workroot (marker files) — but `bun install` itself is never spawned in tests (the `DOBBY_SKIP_INSTALL=1` seam, which still skips only the install inside `up`), so the install spawn's cwd pinning is covered by the later live recipes, not CI.
- **cmux listing stdout format is runtime-unverified** — the pane discovery parser is deliberately tolerant (scan lines for `<kind>:<ref>` tokens, substring-match titles); live cmux pane behavior is covered by the wrap-stage human smoke, not CI (no reachable cmux surface here).
- **Workspace / monorepo detection** — v1 is single-package only (interview decision); `env` reports a flat capability list. The former workspace-grouping machinery was removed with the `capabilities` command. Per-workspace inference is a future arc.
- **The vitest config-less REAL RUN is not CI-tested** — the config-less default for biome + knip is verified through the run() seam with REAL tools (a fixture without a biome.jsonc / knip config), but the REAL vitest/vite/drizzle-kit is NEVER spawned in tests; their `--config`-when-absent resolution is asserted ONLY through the dev/build/db `--dry-run` PLAN text (which renders the resolved `--config <abs>`) and the biome/knip `configs:` note (the same `runner.configArgs` seam), plus the repo's own dogfood gate (its deleted root `vitest.config.ts` forces vitest through the default) — the live recipe covers the real vitest/vite/drizzle spawn. (A STUB vitest bin — a fake `node_modules/vitest` exiting with hand-written reporter JSON — IS spawned by the A2 tests, the same fake-tool precedent as the crashing-vite build fixture, so the A2 advisory + the A1 `parseVitestFailures` parser run through the real step; the stub is not a real vitest run.)
- **The build/test INCLUDE path is untested here for the REAL tools** — the capability-gated build (`vite build`) and test (`vitest run`) steps are exercised in tests on the capability-SKIP path (fixtures without vite/vitest) and, for the INCLUDE path, ONLY through STUB bins (a fake `node_modules/vite`/`node_modules/vitest` exiting with hand-written output — the crashing-vite build fixture + the A2 vitest fixture); running the REAL tools is forbidden by the task. "the REAL build/test run when the capability is present" is covered by the QA's live recipe, not CI. The vitest-step RUNTIME SELECTION (node-if-present, `process.execPath` fallback) lives inside that never-in-CI `runTest`, and its effect is doubly invisible to CI: the suite itself runs under node, so the `node --version` probe always succeeds and both the old (`process.execPath` = node) and new (bare `node`) spawns are node — there is no observable difference and no way to force node absent without breaking the runner. The runtime selection + the fallback-runtime failure note are covered by the QA's live recipe (a `bunx dobby check` under bun-with-node vs bun-without-node), NOT CI — same rationale as the up/down/dev impure paths above.
- **`env`, `check` (incl. `--hook` and `--fix`), the inferred `db:*` tasks, `update`, `dev`, `build`, and the `up`/`down` run-lifecycle pair all exist now.** There is NO standalone `setup` command — it was folded into `up`'s setup phase (STATE.md Findings #32): the user always wants a workspace running when opening it, so `up` prepares AND runs. `setup` therefore hits the ordinary unknown-command path (exit 1 + the `bun update @kvnwolf/dobby` hint), exactly like the removed `commit` command. There is likewise still no `commit` command — the name stays removed (STATE.md Finding #31: `dobby commit` wrapped git for little value) — but the JOB came back mechanized under a different name: **`ship`** (`src/ship.ts`) now owns the whole ceremony (stage-if-nothing-staged → the IN-PROCESS gate → re-stage → `git commit -F` → push → `gh pr create`), which is what the thin wrapper never did: it composes `check()` itself, writes the gate cache the pre-push backstop reads, and owns the trunk/PR policy. What stayed in the `/dobby:commit` SKILL is the JUDGMENT only — which docs to sync, what the message says, whether a PR opens — and `dobby check --fix` remains the standing gate for anything committed outside that skill. The streaming split (part a) landed with `dev`: the bin owns the live streaming path, `run()` stays the capture seam. The `dev` STREAMING execution (inherited-stdio group spawn, the `process.kill(-pid)` group teardown, the SIGINT/SIGTERM forwarding) is NOT CI-tested — the composition is fully covered through `devPlan`'s `--dry-run` plan assertions, but the spawn/kill mechanics need a real server (forbidden in tests), so they are left to the wrap-stage human smoke + the QA's live recipe, exactly as `update` and `db:studio` are handled.
- **`up`/`down` real execution is out of CI reach** — every branch is asserted through the `--dry-run` PLAN (cmux env-var set/unset, neon fixtures with/without `.env.local` creds, teardown extras) plus the early-return paths run for real (up's no-app gate, both fail-hard-outside-git, down's nothing-to-clean no-op, down's stale-pidfile cleanup, a down `teardown[]` extra's file side-effect). The IMPURE work — the curl liveness probe/wait, `bunx neonctl` branch create/delete + the DATABASE_URL* rewrite, cmux pane discovery (`list-panes` + `list-pane-surfaces`, with the runtime-unverified stdout format's tolerant parsing), and the pid-ownership check against a REAL process (`ps` command-line + start-time match) — needs a live server / cmux / neonctl and is covered by the QA's live recipe + the wrap-stage human smoke, NOT CI. Nothing spawns the run itself here anymore — that instruction is text `up` hands to the model, never executed inside this process. down's pane-close instruction and up's liveness curl target are the specific gaps the plan cannot show (down discovers panes live → empty in CI; devUrl is null without portless).
- **`db:*` real execution + `update` are not spawned in tests** — the db:* mapping is asserted only through `--dry-run` (no spawn), and a real `db:*` run in a fixture (no tool installed) is asserted to FAIL, never to succeed; `db:studio` and `update` are interactive (inherit stdio, terminate with the user — the streaming-dispatch prefactor lands in the later `dev` task), covered by the QA's live recipe not CI. A `db:*` command in a project with NO db capability exits 1 with a "no database capability detected" message (a thin-spec gap — no test constrains the wording).
- **Config schema surfacing** — `env` reports project-config presence only (`config: boolean`); `dobby.config.json` carries no worker model/effort/recipe fields at all. Of the `files/setup/teardown/checks` fields, `check` reads `checks[]`, `up` reads `setup[]`, and `down` reads `teardown[]`. `files[]` is skill-consumed (doc-sync), never by the CLI.
- **`kb`/`adr` deliberately do NOT judge, dedup entries, or author bodies** — `kb record` executes a DECIDED record: it never asks whether a concept belongs in the KB (triage/learn decide that from `kb list`), never rewrites an existing record's rationale, and never dedups the BULLETS (recording the identical entry twice yields two bullets — the caller owns that). `adr new` allocates a number and a skeleton; the decision record itself is the architect's to write. There is no `kb remove`/`adr supersede` (the durable artifacts are edited by hand once they exist).
- **The `adr new` collision retry is not black-box reachable** — the handler is synchronous, so no in-process race can be staged through `run()`, and any file sitting at the naive target number is also seen by the max scan. The tests pin the OBSERVABLE guarantee (never overwrite, always a fresh number, `origin/HEAD`-only numbers counted through a real bare-remote fixture); the per-attempt `NNNN-` re-read and the `O_EXCL` fallback under it stand on inspection, and the LIVE cross-worktree collision is a wrap-stage smoke, not CI.
- **`up`'s setup-phase glob support is untested** — the `.worktreeinclude` matcher supports simple `*`/`?` globs (Conductor `file_include_globs` parity) via a bounded tree walk, but the fixed tests exercise only the literal-filename fast path (`.env.local`); the glob branch is covered by real-world use, not CI.
- **The pre-push backstop deliberately stops where the fleet does.** No chain-exec of a foreign hook (no repo in the fleet has one; the marker policy suffices, and chaining is a decision to take with evidence). No staleness bound on the gate cache — `ship`'s `at` timestamp is written but NEVER read: the composite key already invalidates on the things that change a verdict. No pre-COMMIT hook (the commit gate is `ship`'s in-process `check --fix`), no config key to opt out (Decision 7: all consumers; the escape hatch is `git push --no-verify`), and no uninstall command. Two paths stay untested: `check --pre-push` outside a git repository, and the `configHash: null` (no `dobby.config.json`) cache path — the shim's double guard makes the latter unreachable through the hook.
- **The release SPINE knows no target** — `release.ts` knows the PHASES only: everything channel-specific (`npm whoami` + the granular-token/EOTP lore, `bun pm pack` inspection, `npm publish --access public` — never `bun publish` — and, for homebrew, the tap checkout + the cask checksum) lives in a per-target module behind the `ReleaseAdapter` seam. `release-npm.ts` is the npm one and `release-cask.ts` the homebrew one; a `release.type` no module answers to gets a clean "no release adapter for release.type" error (naming what IS registered) rather than a half-release. The spine likewise edits JSON manifests ONLY: a non-JSON lockstep file (mad-eye's `Cargo.toml`, where `version =` also appears under `[dependencies]`) is DELEGATED to the target's `bumpExtras` and reported, because a regex scoped to the `[package]` block is target knowledge. Growing the seam is ADDITIVE by rule — `bumpExtras`/`postRelease` are optional members, so a target that needs neither (npm) is untouched by their existence.
- **The npm adapter gates on the DENY half only** — it refuses a tarball carrying `**/*.test.ts`, `**/__fixtures__/**` or `dist/**` (and an empty one), but never asserts which files a package must CARRY: that is project knowledge, and `release.smoke` is where a project proves the published artifact actually runs. `dist/**` is rooted at the package root by choice (a nested `src/dist/` is not refused). The adapter also never CLEANS a tarball — `--dry-run` writes none (should a real pack ever be added, the cleanup is `find <dir> -maxdepth 1 -name '*.tgz' -delete`, never a bare `*.tgz` glob, which zsh aborts the whole command on when nothing matches).
- **Both built-in targets are registered by the SPINE, so "no adapter" is now unreachable** — `release.ts` holds one `registerReleaseAdapter` line per target (`homebrew-cask`, `npm`) and `run.ts` imports the spine, which is the whole production wiring; the target modules import only TYPES back, so there is no runtime cycle (a self-registering target reached by a side-effect import evaluates BEFORE the spine's registry const and dies in its TDZ — verified). Because `release.type` is a closed set the config validator owns, every value a config can legally carry now has an adapter behind it: `noAdapterMessage` is the landing pad for a THIRD target between the day its type joins the schema and the day its line lands, not a reachable branch today. The registry contract is asserted from the CLI's own entry point (release.test.ts slice 13 drives a `homebrew-cask` config and gets the cask target's own preflight refusal), never only from a test that imported the module itself.
- **The cask smoke never INSTALLS anything** — `brew install --cask` downloads a real dmg, writes to `/Applications` and asks for a password, so the phase hands the command back (plus, ONLY for an un-notarized release, the Homebrew-6 quarantine caveat: casks are quarantined with no opt-out, and `xattr -dr com.apple.quarantine` is what opens an unsigned app) and a human runs it. Nothing verifies the tap's cask through `brew` — not in CI, not in production; `ruby -c` is the only automated check, and it is SKIPPED (with a note) when ruby is not on PATH.
- **The cask scaffold is deliberately incomplete** — the first-release template carries only what a machine can know (token, version, sha256, url, name, homepage, app). `desc`, `zap`, `caveats` and any `depends_on` are left for a human, and a scaffolded file says so in a comment: guessing them would ship wrong metadata to every `brew info`.
- **`release` is never smoke-tested against the real registry** — the suite drives a FAKE adapter and a stub `gh`, over throwaway git repos with a real bare `origin` (so "was it pushed?" is a fact of another repository). What a real `npm publish` / `gh release create` does — and the propagation lag that follows one — is verified by cutting an actual release, not by CI.
- **`artifact-lint.ts`'s `Affected areas` check imports `buildplan.ts`'s `splitCellMembers` — never re-derives an equivalent split.** Two review rounds found the two parsers disagreeing on the SAME cell (a different emphasis character class, then a different stripping position — an interior-decorated area like `` cli/`src`/run.ts `` lints clean while `build-plan` still emits the string WITH the decoration in, so the dispatch protocol's overlap check compares two different strings for one file). `splitCellMembers` (comma-split, EDGE-only emphasis stripped, `NO_VALUE` spellings kept) is the single source of truth for what a cell member string IS; `splitList` layers the `NO_VALUE` drop on top for cells where "nothing here" is legitimate (areas has no such cell — `spec lint` keeps `—` and judges it). A backtick/asterisk left INSIDE an already-edge-stripped area is a distinct lint finding naming the clean form (never silently normalised — build-plan does not clean it up either); `_` is never treated as decoration, interior or edge, because a real snake_case path segment legitimately carries one.
