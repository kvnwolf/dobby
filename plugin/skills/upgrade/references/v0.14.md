# v0.14.0 — direct subagent dispatch replaces the Workflow build loop

## Heads-up: the verifier is renamed to `dobby:qa` — reload before your next execute

`plugin/agents/verifier.md` is gone; its replacement is `plugin/agents/qa.md` (`dobby:qa`), scoped to behaviour proof only — never lint, types, build, or the test suite. This is a rename, not a new agent, and Claude Code registers agents at SESSION STARTUP: a session that was already open when you upgraded keeps the OLD agent registry, so `dobby:qa` will not resolve until you run `/reload-plugins`. On a host where that command isn't available, the only way through is a fresh session. If `/dobby:execute` (or `/dobby:dispatch`, `/dobby:address-review`) reports an unknown agent type after upgrading, this is almost always why — reload or start fresh before trying again.

## Heads-up: the implementor now runs the gate itself

The implementor agent runs `bunx dobby check --fix --baseline` on itself — the **Exit gate** — before handing a task off, inverting the earlier rule that forbade implementors from running any check. This closes the mechanical layer before QA ever sees the task: QA proves real behaviour only now (the browser where an app exists, the artefact directly where none does) and never re-runs lint, types, build, or the test suite. Nothing to configure — the instruction lives in the agent prompt itself.

## Action: the edit hook now reports type errors too

`dobby check --hook` (the PostToolUse Edit/Write hook) still applies biome's safe fixes in place, but now also runs a whole-program `tsc` check and reports the errors that land on the file you just edited — TypeScript has no per-file mode, so the hook always runs it over the whole project and filters the output down to your file. Expect the hook to take a little longer on a large `tsconfig.json`; there's nothing to opt out of, and a pre-existing error elsewhere in the project is never reported at edit time (it surfaces at the implementor's Exit gate / a full `dobby check` instead).

## Heads-up: `dobby env` no longer reports `workflowRecipe`

Worker model and effort now live SOLELY in each of the five agents' own frontmatter under `plugin/agents/` — there is no CLI-side recipe to read or mirror. `bunx dobby env --json` no longer carries a `workflowRecipe` key at all; a skill or script that read it for model/effort/limits has nothing left to read. `/dobby:execute` no longer resolves or validates a recipe object before dispatching — the Architect dispatches the five worker agents directly (the Agent tool, named `subagent_type`), following the dispatch protocol at `plugin/skills/execute/references/build-protocol.md`.

## Heads-up: `dobby build-plan` no longer emits waves

The payload's `waves[[id…]]` field is gone. `build-plan` now returns `tasks[]` with each task's own `dependsOn` (the ids it waits on) and `destructive` flag intact — a task is ready the moment every id it names has reached `done`, with no batch boundary holding it back for anything else. If anything reads the old `waves` field directly, it will find the payload simply doesn't have one anymore.

## Experiment retired

The prior fixed-recipe, seven-day-experiment framing (`baseline-v1`, `cli/src/workflow-recipe.ts`, `maxOuter`/`maxConcurrency`, mechanical-first verification) is gone along with the native Workflow build loop it was designed around. The five worker roles' model/effort are unchanged (researcher Sonnet/medium, test-author Opus/high, implementor Sonnet/high, reviewer Opus/high, qa Sonnet/medium) — only their home moved, from a CLI-computed recipe to each agent's own frontmatter.
