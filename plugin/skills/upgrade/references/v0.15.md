# v0.15.0 — environment adapters become instruction catalogues

The environment-adapter seam changed shape: it used to be code dobby ran on your behalf (opening a cmux pane, spawning `dobby dev`, renaming a workspace); now it is a catalogue of instructions the **model** carries out, because an MCP-controlled host (Claude Desktop, t3 code) gives dobby no way to act there itself — there is no `cmux new-pane` equivalent to shell out to. `up`/`down` still execute everything they always did that isn't host-specific (the setup phase, the liveness probe, Neon branch provisioning, pidfile registration, config `setup[]`/`teardown[]` extras); they just no longer start, stop, or open anything themselves. Four adapters now exist — cmux, terminal, Claude Desktop, t3 code — one file each under `cli/src/adapters/`, detected once per command and queried for a per-topic instruction (`start`, `stop`, `browser`, `rename`).

## Breaking: `dobby env` lost `browserGuide`

`dobby env --json` no longer carries a `browserGuide` field — nine keys now (`branch`, `browserPane`, `capabilities`, `cmux`, `config`, `dbTasks`, `devUrl`, `runPane`, `worktree`). Anything that read `env().browserGuide` gets `undefined`. The replacement is `dobby instructions browser --json`, which answers `{applies, environment, text, topic}` for whichever environment is detected — the same UI-verification protocol, reached through the instruction catalogue instead of a snapshot field.

## Breaking: `dobby up` no longer starts the server

`up` prepares the workspace (the setup phase, unchanged) and PROBES it — it no longer spawns `dobby dev`, opens a cmux pane, or waits for the app to answer before returning. Instead it returns `live: boolean` and `instructions: Instruction[]` (the applicable subset of `rename` then `start`), and the caller — a skill, an agent, you — carries those out and re-invokes `up` to confirm the app is live. Any consumer prose that says "`up` ensures the run is up" or describes `up` as starting the server is stale; the two-step protocol is documented in full at `plugin/skills/execute/references/bring-up.md`, and every stock skill/agent that brings a worktree up (`execute`, `scope`, `dispatch`, `address-review`, `diagnose`, `prototype`, `finish`, `qa`) already follows it. If your own `CLAUDE.md` or a custom skill restates the old "up starts the app" behaviour, update it to point at `bring-up.md` instead.

`down` mirrors the same split: its own mechanics (killing the registered pidfile process, deleting the Neon branch, running `teardown[]` extras) complete before it returns; the only thing left for the caller is `instructions[]` — the `stop` topic, present only when a kit pane was discovered under cmux.

## Breaking: `dev-start-failed` removed, `neon-branch-failed` added

`up`'s `reason` enum lost `dev-start-failed` — `up` starts nothing itself anymore, so there is no start of its own that can fail; a failed start now shows up in the `start` instruction's own command output, observed directly by whoever ran it. `neon-branch-failed` was added for a Neon branch provision that fails (`bunx neonctl` erroring). The current set: `not-a-git-repo` · `config-unreadable` · `install-failed` · `worktree-copy-failed` · `setup-extra-failed` · `neon-creds-missing` · `neon-branch-failed` · `liveness-timeout`.

## Breaking: `dobby dev` refuses a live twin and owns its own pidfile

A live `dobby dev` now registers itself at `<workroot>/.dobby/dev.pid` on startup and clears its own entry on teardown. A second `dobby dev` that finds a live, owned twin already registered there refuses instead of starting a competing server: `already running (pid N) — \`dobby down\` stops it`, exit 1. This is what lets `up`'s in-flight retry find a start already underway instead of handing back another `start` instruction, and what `down` signals to tear a run down regardless of which environment started it.

## New: `down --json`

`dobby down --json` is new: `{cmux, instructions, ok, reason, slug, workroot}` — `reason` a closed set (`not-a-git-repo` · `neon-delete-failed` · `teardown-extra-failed` · `null` on success), `instructions` carrying the `stop` topic only when a kit pane was discovered.

## New: `dobby instructions <topic>`

`dobby instructions start|stop|browser|rename [--json]` prints the environment's instruction for one topic directly — the same catalogue `up`/`down` embed, callable on its own (QA reads `browser` this way; a manual-setup gate can read `start`). It is universal in `--help` (never capability-filtered) and requires a workroot except for `browser`, which degrades gracefully outside a git repo. `applies: false` is a valid answer, not an error — a plain terminal has no workspace to `rename`, and `dobby down` kills the registered process itself, so `stop` never applies there.

Four real adapters now exist under `cli/src/adapters/` — `cmux.ts`, `terminal.ts`, `claude-desktop.ts`, `t3-code.ts` — resolved by a four-rung detection cascade: `CMUX_WORKSPACE_ID` present → cmux; `CLAUDE_CODE_ENTRYPOINT` one of Claude Desktop's three documented values → claude-desktop; `__CFBundleIdentifier` prefixed with the t3 code bundle id (macOS only — t3 code on Linux/Windows falls through to terminal) → t3-code; else terminal, the floor.

## Known limitations

- **t3 code detection is macOS-only.** It reads `__CFBundleIdentifier`, an Info.plist artefact macOS sets for every GUI-hosted process; there is no equivalent signal on Linux/Windows, so t3 code there lands on the terminal adapter instead (its `start`/`stop`/`rename` answers are identical either way — only `browser` differs).
- **The Claude Desktop adapter's browser guide is unverified against a live Desktop.** It's written from a field study dated 2026-08-19 (Claude Desktop 1.30096.5, Claude Code 2.1.229) — `docs/field-studies/claude-desktop-2026-08-19.md` — with the provenance marker restated inside the guide text itself, so replacing it once someone verifies against a live Desktop is visible. The t3-code adapter's guide, by contrast, IS verified (t3 code v0.0.38, 2026-09-02).
- **`.claude/launch.json` stays deliberately unused.** It's a documented Claude Desktop feature; dobby owns the devUrl model through portless instead and does not read or write it.

## Upgrade steps

1. `bun update @kvnwolf/dobby` in each consumer repo.
2. Restart the Claude Code session (or `/reload-plugins`) before your next `/dobby:execute` — `plugin/agents/qa.md`'s `tools:` frontmatter changed (it now names `mcp__claude-in-chrome__*`, `mcp__Claude_Browser__*`, and `mcp__t3-code__*`), and Claude Code registers agent tool access at session startup.
3. If a consumer's `CLAUDE.md` restates the old bring-up behaviour ("`up` starts the app", "`up` opens the browser pane"), re-read `plugin/skills/execute/references/bring-up.md` and update the restatement to point at it instead of duplicating stale prose.
