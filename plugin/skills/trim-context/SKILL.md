Run an **inference-only** sweep: derive candidates from the whole Git workroot, never accept a path-limited request or add runtime/config/tooling work. You are the architect: workers inspect, write, and review; you never edit, stage, commit, or write the ledger — except the single narrow ledger exception in Step 4: promoting each checkpoint's reviewed staging file onto the canonical ledger, and the resulting one-time `git add -f`. Read `references/sweep-contract.md` before the first dispatch — it is the shared contract for inventory, approval, review, and `.dobby/sweeps.json`, whose per-file `trim-context`/`anti-slop` sub-keys let this skill and `/dobby:anti-slop` share the ledger without either one owning or invalidating the other's coverage.

## Step 1: Inventory the workroot

First delegate execution of the read-only, deterministic mechanical extractor `scripts/comment-inventory.mjs` from any directory in the workroot. It walks each supported file's real syntax tree with a vendored, self-contained Tree-sitter parser (never a text/regex heuristic) and emits stable JSON for tracked files only, with comment byte ranges, kinds, totals, and `parsed`, `unsupported`, or `parse-error` coverage. It makes no candidate/retain judgment; its per-file comment-byte totals are the weight/targeting input that later ranks files into lots (Step 3), nothing more. A `parse-error` row is a file this sweep does not cover: name it and its reason in the report, but it does not block ledger finality for any other file. An `unsupported` row for a file type outside the extractor's parser surface (prose, data, lockfiles, and other non-code text the researcher reads in full) or a deliberate symlink/path-traversal exclusion is the extractor's normal, expected result and is not a coverage gap. This inventory is not a repository check or Gate.

Once that mechanical record exists, dispatch a `dobby:researcher` to inventory every eligible FILE (not unit) in the Git workroot, per the contract's one-row-per-file shape, and read the ledger's `trim-context` sub-key wherever it appears — never `anti-slop`'s sub-key or `metrics`, which belong to that other skill alone. Require the contract's path exclusions, cost tiers, per-file eligible-text bytes, expected disposition, known levers, and ledger verdict. No ledger file, or none of this skill's sub-keys yet, starts the contract's full first sweep; a malformed shared container or a malformed `trim-context` sub-key stops before writes.

Group the per-file inventory by tier and track, and rank files within each group by weight — comment bytes from the extractor for the comment track, judgment call for the prose track. This ranking is the lotting input for Step 3, not a batch proposal to approve file-by-file. Do not hide a low-value file by omitting it: a file whose units are all retain is still reported, as a retain row with its reason.

## Step 2: Obtain policy approval

Present the ranked, tiered, tracked inventory and ask for one policy approval covering scope and aggressiveness: which tracks run, how aggressive the trim should be, and what is explicitly excluded. This is the only pre-write approval gate — lots then run without individual approval. Return to this step only when the policy changes (budget moves between tracks, aggressiveness changes), a lot proposes something outside the approved scope, or the sweep hits a blocked/partial outcome. Silence, a general "clean it up" request, or approval of an unrelated policy question is never approval to write. Rejection is an explicit retain; a defer is unresolved and gets no sub-key for its file. On a first sweep, follow the contract's first-full-sweep rule.

## Step 3: Apply approved lots

After policy approval, form lots of 6-8 files by weight, one track per lot (comment-trim or prose densification, never mixed) — a larger lot exhausted an implementor mid-run in the field (13 of 47 files, 430K tokens, 257 tool calls); 6-8 stays inside what one implementor can finish and get reviewed. Give each worker its disjoint file set, its track, the comment and `CONTEXT.md` rules, its expected yield (~5% comments, ~12-14% prose — leaving a file untouched because everything in it is load-bearing is a correct outcome, not underperformance), any levers carried forward from prior lots, and these limits: change human text only, edit with the file-editing tools only — never a shell heredoc or a compound shell pipeline, since the worktree permission guard rejects both — do not stage/commit, do not alter behavior, and do not write the ledger. Size the fan-out yourself: partition independent implementors into deterministic sequential batches you judge safe to run together, launch one batch in parallel, await all its results, then launch the next. Retries and replacement Agents consume a slot.

Validate every writer's `{status, workLog, blocker}` envelope. Collect each lot's reported levers and fold them into later briefs. A blocked or malformed result stops further dispatch into that lot's files only; account for any changed files, do not repair or revert in the architect thread, and follow the partial/error contract.

## Step 4: Review, finalize, and report

For every fully written lot, first run the mechanical check: a filtered `git diff -U0` over that lot's file set must come back empty after stripping comment-syntax lines — proving zero executable lines changed. That proves no executable line changed; it does not prove a removed comment was safe to lose, so every lot — comment or prose — then goes to an independent `dobby:reviewer` that did not author any reviewed file, checking whether surviving text still carries the same action, boundary, and reason and whether every removed comment was safe to lose under the preservation rules (the contract's "Writers, reviewers, and final bytes" names the removed-comment marker classes worth scanning for — a targeting aid, not a completeness proof). Partition independent reviewers into deterministic sequential batches you judge safe to run together: launch one batch in parallel, await all its results, then launch the next; retries and replacement Agents consume a slot. Route findings only to the implementor that owns the affected disjoint set, then re-review (mechanical check again, plus another independent review).

As soon as a lot passes both its mechanical check and its independent review, checkpoint it. Dispatch a separate `dobby:implementor` to stage that lot's resolved sub-keys — changed and explicit-retain files only, from that lot's reviewed final bytes — into this skill's own `trim-context` sub-key, writing the full proposed ledger to `.dobby/sweeps.json.pending`, **never to the canonical `.dobby/sweeps.json`**, prescribed by the contract, always built from the canonical ledger and overwriting any existing `.dobby/sweeps.json.pending` outright rather than reading, merging with, or appending to one; it never touches `anti-slop`'s sub-key, `metrics`, or an earlier lot's already-written sub-keys, and never stages, commits, or writes the canonical file. A different `dobby:reviewer`, briefed with that lot's exact file set, validates that staging file alone, never the canonical file (schema, this skill's `rulesVersion`, sorted keys, exact final-byte hashes, that the increment's added paths match the lot's file set exactly — no path missing, no extra path, none belonging to another lot, the check that fails a stale or misdirected staging file rather than pass it — and that no other lot's or skill's sub-key changed). Only once that review passes do you, the coordinator — never a worker — promote it: a mechanical move of `.dobby/sweeps.json.pending` onto `.dobby/sweeps.json`, before the next lot's checkpoint runs. This checkpoint writer/reviewer pair runs in the same judgment-sized sequential batches as lot writers/reviewers; your promotion is mechanical bookkeeping, not an Agent dispatch. A lot this run does not reach or resolve — parse-error, deferred, blocked, or out of budget — gets no staged increment, no promotion, and no sub-key, and is named in the savings report instead; it never blocks an earlier lot's already-promoted checkpoint. `.dobby/` is gitignored and only `.dobby/sweeps.json` itself is ever force-added, so a failed or interrupted checkpoint leaves at most a stale `.dobby/sweeps.json.pending` — never committed, and simply overwritten by the next checkpoint attempt; no cleanup step is needed. If `.dobby/sweeps.json` is not yet tracked by Git — check with a Git query against the path (e.g. `git ls-files --error-unmatch -- .dobby/sweeps.json`), never by whether the file exists on disk, since an earlier promoted checkpoint interrupted before the force-add can leave it sitting there untracked — follow the contract's "Getting a new ledger tracked" step yourself, immediately after promoting the FIRST checkpoint: `.dobby/` is gitignored, so as coordinator you run `git add -f -- .dobby/sweeps.json` exactly once to bring it under tracking. Promotion and this force-add are your one narrow exception to never staging, committing, or writing the ledger — state them together, always in that order; skip the force-add if the path is already tracked (e.g. `/dobby:anti-slop`, an earlier run, or an earlier checkpoint in this run got it tracked first). Never promote a checkpoint after that lot's partial/error outcome.

Report the contract's savings summary: eligible and changed files, approved/rejected/deferred counts, before/after bytes and estimated tokens by tier and total, comments/`CONTEXT.md` changed, retained/deferred rationale, this skill's `trim-context` ledger rules version, and every unresolved file by name and reason (parse-error, deferred, blocked, out of budget).
